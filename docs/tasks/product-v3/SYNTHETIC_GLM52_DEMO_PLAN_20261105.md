# GLM-5.2编码Agent合成演示方案

2026-11-05讨论稿。用户要求先说明构造、验证及华为追加展示保护，再由本机制作数据与使用prompt。本轮仅核读源码和记录方案，未生成数据、运行分析、修改产品或部署。

## 演示定义

80条左右，建议固定80条；模型标识GLM-5.2，展示为独立合成编码Agent业务。输入集中50,000 Token附近，主问题是system内容中独立billing行的CCH变化；目标全范围Token加权理想命中约36%→90%。不填实际cached、TTFT或吞吐改善值，不声称真实ICSL数据。

独立appid建议demo.synthetic.glm52.cch.v1，common_name使用独立演示服务标签并与GLM-5.2绑定，名称在制作时校验可接受和不冲突；CSV形状沿当前五列hash_id/appid/model_handle_start_time/completion_tokens/request_input。hash/time为明确合成且有序、唯一；completion_tokens为合成占位，标注不用于输出性能/成本推论。主交付仅before CSV；after作为验证参照和诊断评估副本，默认不再导入为第二个监控运行，避免改写演示默认选择。

## 内容与复用结构

虚构同一代码库与编码规范，统一固定工具集/顺序/描述、完整且有效的调用关系；80条是同项目的独立请求快照，不冒称真实连续80轮会话或真实任务质量验证。

system稳定段A（约18.2K）→独立x-anthropic-billing-header行（每条cch唯一、固定宽度）→稳定段B（约27.3K）→其他固定模板/工具内容→变化的当前任务/局部补丁/日志（约4.5K）。分段是Token预算初值，最终以完整GLM模板后位置核算，不按字符估算或拼接单段Token长度。可把A/B置于同一system消息，保持除billing行之外的静态形状完全相同，尾部变化放后续user内容。

素材采用虚构代码模块、接口约定、单元测试说明和不同修改任务；避免同一短串机械重复、不同请求额外时间戳/临时路径、工具漂移、重复大载荷等主动干扰。允许保留真实运行产生的L4等附带观察，不隐藏规则结果，也不要求L1独占所有发现。

80条平均50K、冷账本起点下，忽略整块及模板开销：R约为(79×L)/(80×50,000)。36%需共享约18,228 Token，90%需约45,570 Token。实际扣除块/MTP并考虑尾部共同片段后调节文本边界。CCH若每条唯一且位于全输入开头，修改前接近零，不符合36%；本构造不冒称Claude Code原生头部布局。

长度建议采用固定随机种子的窄钟形目标序列，约48K–53K，中心约50K；调节尾部内容，不调稳定前缀。50K统一指50,000。现有5K桶可能只显现少数柱，不能为了钟形图擅改前端桶或伪造直方图；以真实桶和分位数说明集中性。若希望50K–55K成为唯一众数桶，可在讨论确认后将中心轻微右移，但不承诺50条/80条自然形成光滑高斯。

## 当前实现锚点与验证

- domain.py的GLM-5.2默认block_size=128；effective_block_size还乘cp_world_size，MTP等以现场固定配置为准，不能为凑数字改配置。复用链按appid隔离，前后账本分别冷启动，固定请求顺序与有效分母。
- prefix_analysis/dynamic.py匹配system/developer字符串中行首x-anthropic-billing-header且含cch=的整行；须证明可比静态形状一致、实际槽位变化。修改是移除匹配行，不是任意顶层JSON cch字段替换。
- 本机制作前锁定发布版本、模型Tokenizer/Chat Template修订与摘要、thinking参数、block/CP/MTP、预算及序列化方式。与华为不同则暂停复用计量结论。
- 本机先验证80条都合法、模板成功、长度符合目标；再执行相同监控/L1/plan/full evaluation路径，证明卡片/位置/修改/完整80条评估链条。直接手工after回放只能校验结果，不能代替L1实际方案成功。
- 按sum(H)/sum(P)计算命中，不平均单请求百分比。目标建议35.5%–36.5%和89.5%–90.5%，展示真实精度；不能手工写36.00/90.00。保存P/H/C、每条指标与前后原文摘要，不把54pp提高换算成实际TTFT/吞吐。
- 自动pilot只是准备阶段，最终必须是完整80条评估。不要求穷举所有请求对；召回/扫描/保留覆盖及partial理由如实记录。不能隐去预算截断或补Token recipe让页面显得成功。
- 小范围负对照在本机隔离运行：CCH固定的请求不应产生变化CCH的L1候选；删除行后不再存在该候选。它们不混入80条展示分母、不默认传入现场目录。
- 约400万输入Token只是逻辑规模，实际JSON、Python对象、索引、plan和保留副本另计。记录阶段峰值、时间、输入/产物字节，先预算后运行，不能因只有80条就忽略现场32GiB限额。

## 追加展示的关键风险

只读源码发现：user_monitoring/discovery.py按新注册运行优先遍历，is_default是appid/model/common_name组合内默认；UserMonitor.tsx无run/appid的初始入口取目录第一条默认项。因此独立appid能保护真实业务组合的默认历史，但不能保证无参数入口仍首先显示真实数据。不能通过手改SQLite rowid、倒填时间或改目录文件掩盖这个问题。

固定用户链接已有#/users?run=...&appid=...&revision=...；异常页已有binding/task/direction/mode=history。固定链接可保护指向原结果，但不是所有裸入口默认不变的充分保证。当前未发现“发布但不进入全局初始默认”的现成参数。

严格保护门槛：既有真实输入/结果/manifest身份不变，真实appid组合默认不变；旧固定链接、裸入口首次打开、刷新、新浏览器及四入口均按约定保留真实展示；演示需明确选择独立appid/任务才能进入。仅允许演示目录项新增，不允许混入原真实运行的榜单/统计。

制作后先在本机隔离state放置代表性既有运行，按现场版本演练追加与默认选择；不拷贝扩大真实数据访问。若无法保持裸入口，必须在华为导入前报告具体差异，另行确认最小默认隔离调整方案；本轮不授权改产品，不以保留固定链接冒充全部不影响，也不直接导入碰碰运气。

## 华为执行prompt应包含的步骤

1. 核版本/SHA和模型资产，确认受控输入目录现有挂载；新增单独demo子目录，不覆盖任何文件，不改已有挂载/镜像/state。新数据若需改挂载或重启则停止说明。
2. 只读保存真实运行目录、组合默认、任务与报告身份/摘要、四入口基线链接。共享数据库会新增记录，不能要求数据库整文件SHA不变；核旧记录与封存成果不变。备份按已有安全机制，不清理真实数据释放空间。
3. 确认默认隔离方案已验证、预算与资源余量充分，无其它分析任务并发；有峰值压力就停止提交，不提高mem_limit或取消别人的任务。
4. 使用支持的API新建80条演示监控运行，再绑定同来源的异常任务；唯一submission_key、源revision及任务身份留档，重试先查原任务，不重复盲投。L1来自现有规则，无自定义插件或全局recipe变更。
5. 核查L1证据、真实生成plan、完整前后评估80条，和本机清单对齐；预算/部分状态不合格就停在报告，不伪装ready。
6. 明确选择demo appid展示，生成固定演示链接；保留原真实固定链接与入口。不要用after单独监控运行覆盖before默认。
7. 前后核对旧真实组合、完整指标、原文/报告身份与四入口行为；容器/API健康记录。未通过不宣布追加成功，不自行恢复整个旧state覆盖新结果；取消/撤回仅限本次demo且须使用已验证机制。
8. 在唯一Markdown回传中独立新增“合成演示验证”章节：清单SHA、运行/任务/索引身份、实际数值、资源、覆盖、默认入口和真实结果保护证据、异常/停止原因。与原真实验收章节分开。
