# TokenScope V2 推广准备：听众画像 r0

2026-11-04。依据用户本轮描述建立，属于讨论用画像；未访谈验证的动机/痛点标为假设。本轮仅构建画像，展示内容、最应记住的能力和价值、讲述顺序及材料形式留到下一轮。

## 1. 当前工作安排与定位

七项研究判断保留，华为报告回传后逐项用数据确认，再集中讨论仍无法解释的问题；暂不进入V3实施。当前转向V2资料整理与推广准备。V2已有完整功能与本机验收/交付记录，可以着手内部介绍；现场验收和量化收益仍按实际证据说明，不把未验证能力或V3设想归入V2成果。

用户提出的产品定位：Token监控，连接业务需求与AI基础设施优化。

- 向上服务应用/业务方：观察用户行为、刻画业务流量、分析理想命中及优化机会；结合命中与计算情景辅助讨论合理SLO。
- 向下服务AI infra建设者：用真实流量与复用特征支持路由、负载均衡、KV-aware、压测负载与并发等薄弱环节的针对性优化。

以上是产品服务定位，不意味着V2已实现自动优化、自动调参或真实SLO保障。当前可观测、可分析、可参考的能力与未来执行优化分别核对。主听众是要理解价值与判断投入的领导；产品直接服务对象是应用方与infra建设者，两者不混同。

## 2. 主听众：有工程经历、缺少当前AI服务上下文的管理者

已知特征来自用户描述：有基本逻辑思考能力；了解业务流程、开发与运维工作，可能曾任开发/运维工程师；理解TTFT/TPOT等宏观性能概念；不熟悉本项目专有计量和MaaS组件关系。不能把“缺少AI上下文”误当成“技术理解能力弱”。

| 画像维度 | 当前判断 | 对沟通的要求 |
| --- | --- | --- |
| 已有经验 | 理解定位问题、人工排查、发布验收、资源配置、稳定性和研发投入 | 可借助熟悉的工程任务解释价值，不必从计算机基础讲起 |
| 已知性能概念 | 知道首Token慢、生成慢及服务目标的重要性 | 仍需解释监控时间范围和数据来源，避免默认为同一种端到端指标 |
| 缺少的上下文 | chat template、prefix复用计数、理想/真实命中、req/s、AI任务形态、GB/GF/MA及采集来源 | 新术语出现时说明它解决哪个问题；组件缩写不能作为理解产品价值的前提 |
| 可能承担的决策 | 是否认可需求、支持试用/推广、安排应用或平台团队配合、继续投入维护 | 需要知道适用对象、实际可用范围、投入和责任边界；具体权限待确认 |
| 可能关心的回报 | 减少人工调查、缩短定位周期、提高资源利用、改善性能目标制定、减少盲目调参 | 这些是待证价值假设；人时/成本/收益必须有前后对照才量化 |
| 可能担心的成本 | 新工具接入与维护、数据可得性、判断是否可信、是否新增沟通/告警负担 | 需要可信来源和适用范围；不默认其担忧已被访谈证实 |

## 3. 从主听众中区分的两类决策视角

这两类是决策视角，同一位领导可能兼具，不按职级、年龄或部门名称臆造人群。

| 视角 | 主要责任/关切（待验证假设） | 他们可能追问 | 能建立信任的证据类型 |
| --- | --- | --- | --- |
| 业务与研发负责人 | 应用交付、体验目标、团队人力及跨团队协调 | 哪些应用适用？原来谁花多少时间做？工具结论能指导谁采取什么行动？业务质量会受影响吗？ | 清楚的使用任务、人工流程对照、可核验案例、业务方复核和明确边界 |
| 平台与运维负责人 | 服务稳定、资源效率、容量与配置、排障和维护 | 和已有监控是什么关系？数值是否可信？能减少哪类盲区？配置变化后如何确认改善？ | 采集/计量解释、可重复的结果、已验证范围、异常/缺数处理和维护成本 |

不能将“命中高”直接翻译为“业务体验好”，也不能将“看得到问题”直接翻译为“保证不发生稳定性问题”。他们的工程经历使其很可能追问因果、反例、复现和责任，而不仅关注界面是否丰富。

## 4. 次要听众及与领导的关系

| 听众 | 角色与已有上下文 | 特别需要理解的内容类型 |
| --- | --- | --- |
| 应用开发者/业务接入负责人 | 了解自己的调用与质量要求，未必了解缓存、模板和推理调度 | 分析结果与自己可改动内容之间的关系，必要业务内容是否被误判，复核与使用成本 |
| infra/推理平台维护者 | 了解资源与引擎，未必了解每家业务流量 | 用户行为与系统指标之间的联系、结论能支持哪些配置研究、适用范围与验证证据 |
| 一般同事/潜在推广者 | 熟悉团队流程，对模型服务了解不一 | 自己是否有相关问题、什么时候找谁使用、怎样正确转述产品范围 |

主听众负责判断价值与组织采用；次要听众既可能实际使用，也可能为领导验证实用性。不能用一套过于简化的承诺说服领导，却让实际使用者发现产品做不到。

## 5. 听众的认知起点与误解风险

- “Token”可能只被理解成计费单位，尚未理解输入组成和重复处理与资源/时延的关系。
- “理想命中”可能被误读为生产已达到的命中，或产品承诺一定能达到的目标。
- “真实命中”可能被误读为未经审计也可靠的物理复用实测。
- “监控”可能被理解为既有性能看板、实时告警平台或自动处置系统；具体覆盖需用版本事实澄清。
- “SLO参考”可能被误读为保证业务体验；当前参数假设和模型侧/端到端范围需易懂地说明。
- “向下优化”可能被误读为V2会自行更改生产路由、并发和P/D配置。

这些是传播中的可能误解，不是假定听众不懂逻辑。下一轮选择内容时应让听众能建立正确关系，而不是要求其记住所有术语定义。

## 6. 听众判断产品的可能路径

首先判断自己负责的业务/平台是否有这个问题；随后判断工具是否能提供过去缺少或昂贵的信息；再判断结论是否可信、能由谁转为行动，以及接入/维护成本是否值得。该路径为画像假设，不预先冻结宣传结构或核心卖点。

对其已有工程经验，预计以下表达偏好更合适：具体任务与可复核证据、清楚的前后区别、明确的适用条件；收益数字能够解释计算方法。对于效果有限、数据缺失和待验范围，能说明其影响比使用绝对保证更可信。

## 7. 仍待确认的听众差异

本轮不将其作为阻塞：实际听众偏业务/研发还是平台/运维；其可批准的是试用、资源投入还是规模推广；此前是否见过TokenScope及既有监控；他们正在经历的排障/成本问题；实际材料使用场合与可投入时间。下一轮如影响取舍，再按需要确认，不凭空给听众设定时长、预算或业务规模。

## 8. 画像的可检查标准

下一轮讨论内容时，用本画像检查：听众是否能在不理解内部缩写的情况下判断与自身责任的关系；是否能区分已验证事实、分析参考与优化设想；是否知道结论由谁使用、谁负责行动；是否能提出有意义的投入/收益和适用性问题。本轮不决定核心能力排序或演示目录。
