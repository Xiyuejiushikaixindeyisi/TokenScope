# Token长尾回传判断：异常是否成立、V3.5是否值得开发

2026-11-10。本轮只分析Token异常证据与V3.5投入必要性，不给V3四P0实施方案。V3开发会话正在细化范围、顺序与验收；待用户交来后，本研究会话仅作简要评审。Token私有修复仍留V3.5，当前不实施。

依据：[华为回传](../../huawei/TOKENSCOPE_V35_TOKEN_TAIL_EXPLORATION_20261110.md)，34,994字节、661行，SHA256 `1c617fc0afbb2f825253ab58aa2b4423f8a1983c939af516e2bcc21ee3167ab0`。报告声明来源为HV2/c1345b6。已定向读取当前token_content及建议管线代码，相关代码相对c1345b6无差异；仅核对代码与表内算术，未读取现场原始请求、运行分析器或复现编码/仿真。

## 结论

**有真实的长请求结构、大工具返回和重复载荷线索，值得排查；尚未证明这些业务普遍存在可无损删除的Token浪费。V3.5有针对性完善Token异常分析能力的价值，但本报告不足以支持推倒重做T2–T4、统一开启截断策略或承诺具体节省比例。**

“长度异常”需要业务/同类场景基线；同一appid内混合短问答和长编程对话会形成均值与众数差距，不能直接归为错误。重复事实、违反明确业务策略、可安全修复及线上性能收益是不同结论。

## T2–T4是否方向错误

报告三处写明这三组在discovery catalog中没有匹配的既有诊断任务（报告237–255、350–361、446–459行）。因此本批不能作为“运行T2–T4后漏检”的直接证据；历史用户对其他任务的体验仍需另行解释。本报告的“若执行时”是预测，不是执行验收；目录分页/完整性取证也未完整嵌正文。

当前代码可确认以下事实：

- T2/T4仍会生成内容清单观察，`content_inventory`本身condition为`met`；没有适用policy时，规则结论是`unknown / NO_APPLICABLE_POLICY`，不会生成“超过业务策略”的finding。报告将事实观察也写为unknown不准确。依据：[rules.py](../../../src/tokenscope/token_content/rules.py:105)，尤其158、237–268行。
- Token建议阶段在bundle无recipes时跳过并记录`NO_CONFIGURED_RECIPES`。这与有没有提取/观察不同，也不自动等于部署bug；没有业务保留依据，不应凭默认数字判定可删。依据：[recommendation_pipeline.py](../../../src/tokenscope/analysis_common/recommendation_pipeline.py:53)。本机代码支持该条件分支，不能代替现场配置快照证明三组实际配置。
- T3已有同请求精确载荷重复观察，且会排除祖先/子容器重叠；哈希分桶后还核对完整规范化值，不是只比SHA。输出明确将saved_tokens、deletion_safe和execution_count留空。依据：[duplicates.py](../../../src/tokenscope/token_content/duplicates.py:28)。报告的8组是否满足全部候选/重叠条件，未跑该规则，不能直接写“T3必产8组”。
- assistant正文已被提取并计量，T2/T4只选tool_result，故缺口是规则/解释的覆盖，不是assistant内容完全不可得。system/developer则不在当前提取的role名单中；报告称system已作为message_payload提取，与代码不符。依据：[extraction.py](../../../src/tokenscope/token_content/extraction.py:226)、[measurements.py](../../../src/tokenscope/token_content/measurements.py:8)。这些度量为字符/字节/行等，不是完整模板中的精确字段Token贡献。

所以T2大返回、T3重复、T4历史工具结果仍与样本有关；现有能力可复用。可确认的是：当前规则覆盖不完整、业务策略与事实观察的边界容易被“零建议”掩盖；尚不能确认三组有哪一个生产执行bug。

## 对照结果应如何解读

报告4.2表共有六个before/after对照，所有行均满足C=P−H。按报告整数重算如下，**只验证算术，不代表复现原样本**：

| 组/窗 | 输入P变化 | 未命中量C变化 | 理想命中率变化 |
| --- | ---: | ---: | ---: |
| 天舟/A | -39.62% | -12.47% | -6.30个百分点 |
| 天舟/B | -17.89% | -16.48% | -0.87个百分点 |
| Qwen/A | -31.12% | -24.08% | -5.02个百分点 |
| Qwen/B | -45.21% | -36.85% | -7.16个百分点 |
| GLM/A | -35.87% | -26.59% | -3.93个百分点 |
| GLM/B | -17.70% | -18.74% | +0.86个百分点 |

六组C均下降、五组命中率下降。这支持“裁剪历史可能减少输入和未命中量”的探索价值，不能单以命中率不降作为Token优化标准。删除大量已可复用的Token，本身就可能使H/P降低，未必意味着保留内容产生额外缓存失配；报告据此断言stub破坏缓存连续性、Qwen较大block_size造成更大损失，缺少控制变量或保留内容前缀映射对照。

所有试验仅保留最近3个工具结果，报告明确承认可能破坏任务质量，未验证答案/任务完成率。该变换还用原内容长度生成stub；没有实际编码/仿真调用和完整样本键，无法区分删除可复用内容、动态stub及其他变化各自的作用。因此表中比例暂不能作为可兑现节省或正式验收依据。

## 必须保留的报告局限

1. GLM“长尾全部使用57K system和18工具”的概括（410行）与前文14/292该system、47/292该tools以及最长例1工具/2,568字符冲突；长尾90条的system均值又只有14,213字符。可保留最长例事实，不推广为全部长尾。
2. 编码次数写1,440（160行），其公式实际为720，后表也为720；六个配对窗口却写“8/12窗口命中率下降”（509行），正确为5/6。ΔC/ΔP绝对差值比率约0.044–0.722，亦不等于报告0.12–0.82。
3. 附录A没有样本键清单或实际SHA，只指向未回传JSON；Qwen/GLM input_sha留占位，未完整列revision与复核集结果。正文只有修改函数，没有统一编码/仿真关键调用，单文档无法复算原试验。
4. 分层样本刻意超采长尾，不能外推异常占比；系统模板原始SHA并非已经验证的业务场景族。字符相关性、单请求历史快照均不能证明无限Loop、历史已经无用或业务必要性。
5. 小样本独立脚本成功及容器内存读数不能证明产品mem_limit/完整流水线问题已解决；需区分自有计算峰值、容器末态和真实产品链路。本轮不据此给资源性能承诺。

## V3.5投入判断

**认可有针对性开发的必要性，尚不足以认可具体新分析器清单。** 业务价值是让用户知道长在哪里、重复在哪里、哪些已有业务约束被违反，以及哪些只是候选而不能删；现有工具结果规则及精确重复能力应先视为可复用资产。

三类价值有证据支撑：有限范围内能够完成排查；对system/assistant/工具内容及混合场景给可解释的事实；把未执行、无策略、无改法、未评估与真正无异常区分清楚。这些价值不以确认所有长尾都异常为前提，也不等于现在批准具体代码方案。

本轮不采纳报告建议的默认retain_last=3、默认limit、命中率不得下降门槛，或把固定system重复直接作为异常。是否需要新规则、配置体验修复还是结果解释改进，应在V3.5范围讨论中区分；不提前把Token私有功能塞入V3。本轮未改源码/测试/契约/配置/服务/HTML/原报告，未执行远端分析、发送消息或提交Git。
