## 3. 已有材料纠正r0中的笼统未知项

依据TokenScope的[MAAS_REFERENCE（2026-10-30）](../../architecture/MAAS_REFERENCE.md)：

- GB确实对模板前原始JSON做tokenization用于规格分流；与模型套Template后的P不是同一计量对象。当前耗时及可节省份额仍待报告。
- 同一MA UUID内所有P节点、不同appid共享prefix cache已经由用户确认。不能再把“实例内是否允许跨appid共享”当全部未知。不同UUID不据此假定共享。
- hash_id在架构上贯穿GB/GF/motor/P/D；实际导出是否完整、重复/重试如何处理及可关联比例仍待数据验证。
- 当前用户提供的架构说明中，model_ttft从GF发出请求开始，不包含GB排队。新报告确认具体端点；模型侧达标和端到端体验分开。降低GB并发可能增加GB等待/拒绝，必须联合评价。
- 用户侧按appid×模型服务隔离回放；MA按规格×UUID并允许跨appid复用，两种理想指标作用域不同。重点不只是统计分母，也包括共享域与预热条件。

这些是已有架构事实/用户说明的复核，不是本轮新测量，不改变旧契约。

## 4. 与llm-slo-scheduler配套的准确范围

仅定向只读参考了 `/home/zhangxiyue/llm-slo-scheduler/README.md` 与 `docs/admission/G5_GF_DUAL_QUEUE_IMPLEMENTATION_DESIGN.md`；未写入、运行、提交或接管兄弟项目。

其当前材料描述在GF入口使用普通FIFO与让行LIFO、成本分类/额度/压力门控/年龄保护。它不能简化成“所有长请求无条件永久低优先级”，也不是GB粗规格分流本身。其现场收益与阈值仍需其自身验证。TokenScope可研究提供画像和效果解释，执行调度由该项目/平台负责。

配套待验证点：长输入未必高prefill成本（可能高命中），短输入也可能长输出；分流/调度要看未缓存输入与输出负担。统计全体成功请求并列出失败、取消、未完成和最长等待，避免只保护多数请求后把少数长请求排除在报表外。不移植兄弟项目NPU硬件、g5参数或实验结论到TokenScope当前V100交付。

1. 先核版本、预算、源身份、数据质量与可用范围；维持V2用户监控→MA→用户指定后异常的现场顺序。

3. 把已解释部分收敛成讨论结论，把仍无法解释部分列成问题：已有证据、竞争解释、最小区分证据、预计成本。优先利用现有报告/结果，不自动追加现场任务。
4. 再集中研究剩余问题，包括低复用三类区分、实际KV-aware参数折衷、众数画像与准入配合、现有MA参数调优。不重做整轮泛化调研，不先实施。
