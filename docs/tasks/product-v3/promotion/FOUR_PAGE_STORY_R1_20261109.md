## 第一页：现网数据驱动业务与平台协同优化

上部业务流程：现网数据分析 → 识别异常用户/实例 → 提供证据与改进方向 → 协同改进与复核。

- 用户线：逐appid×模型分析理想命中率与请求分布；发现偏离业务预期的行为，提供定位证据、修改方案及评估结果，由业务团队修改并验证业务效果。
- 平台线：逐实例UUID分析命中、流量与长度分布；发现异常或差距，形成路由、压测、并发等验证对象，由MaaS/推理团队试验并验证吞吐与时延改善。分析工具不直接承诺或自动执行模型加速。

下部目标产品架构按用户指定三大块组织，SLO作为用户分析与异常分析之间的桥接模块：

| 模块 | 展示内容 | 业务输出 |
| --- | --- | --- |
| 用户现网数据分析（CPU） | 数据转化：Qwen/DeepSeek/GLM，JSON→Token ID；仿真器：MLA/GDA/CSA，Token ID→理想命中率；数据统计/请求分布直方图 | 当前流量是什么样，当前请求结构有多少复用空间 |
| P90 TTFT与命中率关系（目标能力） | SLO要求+时延参数+现网负载 → XGBoost时延预测 → 按候选命中率求满足目标的最低值 | 目标命中率与SLO参考 |
| 异常分析 | 低命中率分析；Token异常分析 | 差异证据、修改方案与收益评估 |
| MaaS数据监控 | 理想/实际报告命中对比；req/s、Token/s趋势；长度分布 | 平台优化对象与验证方向 |

“JSON→Token ID”和“Token ID→理想命中率”按用户意图作为红字重点。未来XGBoost模块仍需负载与服务参数、训练覆盖和验证支持；图上可简化，底稿不将它误写成两个数直接决定生产最低命中率。现阶段现场可展示参数化SLO参考，不能声称它已经是拟合完成的XGBoost。

页底价值建议：同一份现网证据，支撑业务改进与平台优化，减少跨团队排查和反复试错。

## 第二页：ICSL从优化依据到可执行方案

## 第四页：按负载场景分类，优先协同改善长输入低命中业务

用户所称“四维分布图”落实为两个坐标轴、四个象限。它同时承担场景分类和优化方向说明，覆盖前稿只称“筛选图”的表达。象限按实际行为特征确定，典型业务场景作为解释，不把推断标签冒充已确认的任务语义。

| 象限 | 典型场景解释 | 主要动作 |
| --- | --- | --- |
| 长输入、高命中 | 稳定长前缀的编码/工具型Agent等 | 优化剩余计算与平台路由、并发、调度；关注SLO |
| 长输入、低命中 | 优先协同改进的问题区域 | 核查动态前缀、工具/消息组织与必要业务输入，先定位可修复问题再评估 |
| 短输入、高命中 | 固定模板、标准化任务等 | 关注高频服务效率、并发和排队 |
| 短输入、低命中 | 普通问答、搜索、信息提取等常见LLM任务 | 围绕真实负载、SLO和调度适配；有证据时仍改进可复用部分 |

长输入低命中可能包含必要的独特长文档，不能预先保证全部可提高命中；Agent问题也可能落在此象限，不能由于低命中取消其Agent任务属性。图上突出可行动的分类，底稿保存典型场景与确定业务标签的区别。

### 坐标与既有结果复用

- 每点为appid×模型，避免同一appid跨模型结果合并失真；产品名优先可读，详细表保留appid。
- 横轴使用用户指定方法：L_est = Σ(区间请求数 / 总有效请求数 × 区间右端点)，数据取套chat template后的prompt_tokens直方图，不取JSON分词长度，不重新计算编码。
- 图轴标“平均输入长度（估算）”，脚注“基于直方图区间右端点加权”。这是偏高的近似均值；固定有限分箱时高估不超过箱宽，阈值附近可跨象限。
- 当前源码`src/tokenscope/monitoring/statistics.py`已预计算1000/2000/5000三档。建议同一图统一使用现有1000档，减少近似误差；不逐appid选不同分箱。分界附近保留边界提示，不为使特定案例入选而调阈值。
- 200K以上存在upper=null的溢出箱：计数为0则跳过；非0时需已有summary.max_length才能作明确标注的上界替代，缺少则标不可估算。不得把200K当其右端点或丢弃这些请求。该项在后续prompt写明，无需读取原文。
- 纵轴直接读取同一结果的Token加权理想命中率H/P，不混真实cached；记录数据窗口/run/revision，排除构造样本与重复历史快照。数据窗口不一致时标明，不能伪称同一天的完整总体。
- 高低命中率可讨论50%分界；长短输入分界尚未确定，20K是前一轮Agent示例、8K是普通任务示例，不能将两个数同时作为四象限唯一竖线。最终prompt保留明确参数，确认后再固定。
