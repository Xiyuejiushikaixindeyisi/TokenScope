输入是什么

模型处理的是Token

对话和工具内容按模型格式组织，再编码成Token。请求JSON的所有字段并不都会原样进入模型。

为什么能省计算

相同开头，可以复用

前缀缓存保存相同输入开头的中间计算结果，减少重复处理，并不是直接返回以前的答案。

理想命中基于指定请求与仿真规则；实际复用还受请求分发、缓存状态等因素影响。

现有探测器能查什么？八个通俗例子
规则容易理解的例子判断边界
L1 动态内容固定说明中插入变化的时间、路径或已知CCH行。限已实现语法；业务必要信息不能随意删除。
L2 工具顺序同一组“查合同、查客户”工具，每次顺序不同。集合和定义须相同，不重排消息或调用时序。
L3 工具漂移同一工具描述混入不同临时路径，或定义发生变化。合法版本、权限变更不等于错误。
L4 历史差异可比请求中原有消息被修改或消失。缺可靠会话关联时，不能证明同一会话被改写。
L5 表示差异相同工具结果JSON出现不同格式表示。须核实际Token变化；不把所有JSON变化当等价。
T2 工具返回只需金额，却返回完整合同列表和附加字段。大不等于错，裁剪需业务依据。
T3 载荷重复同一请求多处携带同一份完整合同。重复事实不等于可删除，也不能据此判断Loop。
T4 历史负担约定只留最近结果，仍携带较早结果。需要明确保留策略，正常历史增长不是浪费。

规则来自公开工程实践、前期案例与本地正反例验证。当前列表说明实现范围；本次华为已列4个partial任务的差异组均为L4，Token建议为0，不等于全部业务无问题。T1仅历史兼容，不列为当前展示能力。

从一个业务，展开到优先处理的人群

搜索与排行帮助运营同事在已分析范围内筛选对象，把有限排障精力用在影响大的地方。

看影响面

请求多、计算负担大

先关注优化后可能影响更多流量的业务。

找调查线索

复用偏低、值得检查

结合任务结构判断，不用统一阈值给所有业务判错。

看绝对工作量

高命中，也可能有空间

高命中率与较大剩余计算量可以同时存在。

现场报告支持三模型77个appid×模型目录项，非77个独立appid；搜索排行的多模型入口仍有可达性限制。

不必先准备一套推理环境

CPU

06 / SLO参考

目标要定得合理
先把业务负载放进讨论

不是每个业务都能大幅提升复用。对于内容变化多、优化空间有限的请求，TokenScope帮助把服务目标、等待预算与输入工作量放在一起讨论。

参数化情景参考当前V2
业务输入P90请求长度
期望目标P90 TTFT
运行假设等待时间与处理参数
给出指定条件下的复用需求参考帮助讨论目标与假设，不是线上达标保证。

目标更紧，会提出什么要求？

在同一处理假设下，留给输入计算的预算更少，可能需要更高复用。

等待占用更多时间，怎么办？

识别需要进一步讨论队列、负载和服务目标的条件。

业务复用空间有限，怎么办？

结合实际任务确认约束，避免给所有业务套用同一个命中目标。

让“我们希望多快”与“当前业务需要多少处理工作”能够一起讨论，为服务目标设定补充依据。

当前为未校准参数参考，未接入XGBoost；聚合理想命中不能直接判定P90达标，也不能据此输出安全并发或限流值。

01 / 压测代表性

压测像真实业务吗？

真实请求的长度、量级与复用，和当前压测负载是否一致？

对照真实画像，识别需要补充的场景，同时保留长尾与压力测试。

02 / 场景与配置

配置适合实际任务吗？

不同实例承载了怎样的请求与计算负担？

为规格、并发、Token预算和PD配置的验证选择对象。

支持的决定先在哪些实例做有针对性的验证。
03 / KV-aware路由

分发是否影响复用？

用户与实例视角的差异，是否值得进一步调查？

先对齐请求范围和计量条件，再分析局部复用与负载、排队之间的权衡。

支持的决定是否优先检查路由策略与参数。
04 / 数据与协议

看到的指标可信吗？

缺失、异常cached与注册映射，发生在哪个环节？

显示指标可用性和缺数原因，为采集与接口核对提供线索。

支持的决定哪些字段需要补证，由谁核对。

现有画像与指标支持选择调查对象，不等于已自动推荐配置。当前证据未确认约20个百分点路由损失、缓存容量充分、实例配比错误或压测失配程度。

把真实请求变成共同依据
让排查、协作和优化更有方向
