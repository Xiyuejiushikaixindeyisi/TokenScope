## 1. 建议与证据强度

建议把V3定义为“可信数据上的场景分诊与优化决策支持”：先解释哪些指标可比较，再识别值得优化的工作量，最后把请求交给合适的诊断、SLO评估、路由评估或压测配方。以业务质量、SLO和单位资源有效产出评估价值，命中率仅为中间指标。

七项观察都有可研究的价值，但证据成熟度不同。当前能确定计量和产品边界；不能确定现场最优路由参数、实例数量或真实性能提升。首版设计不依赖华为新报告，新报告用于修订证据和优先级。

| 判断 | 当前结论 | 证据性质 |
| --- | --- | --- |
| 短请求低复用 | 可能业务固有，也可能前部动态字段损坏稳定前缀；短不能单独定性 | 用户观察＋机制推论，现场待核 |
| 高命中继续优化 | 同样10个百分点可能显著减少剩余输入工作，但实际收益随瓶颈变化 | 代数事实；时延/吞吐待测 |
| 95%拐点 | 找到特定KV搬运场景的相关出处，未证实通用阈值 | 厂商一手实验/模型，外推受限 |
| 行为群组 | 可用于负载配方和候选放置；长度相近不能证明前缀亲和 | 文献机制＋待验证设计 |
| 真实8K与压测 | 应审计联合分布；目前无依据输出现场实例配比 | 用户观察，压测原件和服务曲线待补 |
| 数据可信性 | 必须按指标、来源和分母判定，缺失与合法0分开 | 当前产品与旧现场证据支持 |
| MA差距 | 先解决同集合可比性，再做路由/实例内损失分解 | 当前源码与计量推导 |

## 2. 先固定“命中”的四种含义

以同一可比请求集合S为前提，P_i为固定Tokenizer/Template后输入长度。下面均采用Token加权，不能平均请求命中率代替。

- **逻辑理想复用**：h_ideal=ΣH_i/ΣP_i。受作用域、时间顺序、预热、块大小、MTP等规则限定；当前TokenScope逻辑账本无KV张量与物理容量/驱逐。
- **接口报告命中**：h_reported=Σcached_i/Σprompt_db_i。来源可能为计费、协议映射、引擎统计；只有来源语义核实后才能进一步解释。
- **引擎实际复用**：跳过了多少原本需要执行的prefill工作，需引擎计数/事件与请求关联；cache lookup命中、KV加载成功、实际跳过计算未必同一事件。
- **性能收益**：相同业务质量和可比负载下TTFT、TPOT、完成时延、SLO达标率、goodput或成本改善。不是某个命中字段的别名。

每个指标同时携带N_total/N_eligible/N_valid/N_checked、Token分母、排除原因、来源及模型身份。旧10appid的676样本只支持其选择范围内的结构结论；它与新增短任务观察可以同时成立。不能从DS五个工具型样本推广至DS总体，亦不能从新增Qwen短任务否定旧样本。

## 3. V3-01：场景分诊与“低潜力”

业务分类粒度建议为appid×模型服务/制品×模板族×时间窗，允许同appid多场景并存。语义任务名称来自业务注册或人工确认；结构特征只支持“无工具短输入”“多轮工具链”等候选标签。意图识别、实体抽取也可能有长固定指令和few-shot；工具型任务同样可能大多是唯一内容。

分诊必须区分：①存在可消除前缀差异；②有业务证据支持的低潜力；③扫描充分但尚未发现候选；④规则不适用；⑤数据/关联不足；⑥预算截断。只有①才进入优化验证，②才可建议降低提示词优化优先级；其余状态不能冒充“没有问题”。

“低潜力”证据至少包含适用探测器覆盖、固定前缀/变量位置、业务必要性复核、时间留出稳定性，以及候选可节省Token总量的上界或保守估计。优化排序同时看绝对未命中输入量、请求量、业务质量风险和可验证性；不单看命中百分比。低潜力场景转入SLO/等待诊断时，依然需要相应的性能证据。

APC主要减少prefill，缺少共享前缀或decode占主导时收益受限，[vLLM功能文档](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)支持这一分诊。现有L1–L5、T2–T4适配要先核覆盖与合法负例，再考虑新增候选；HV2已经修复旧预算与展示问题，旧报告的截断不作为新版bug证据。

## 4. V3-02：85→95%的价值及95%出处

在输入总量不变且h口径相同时，未缓存输入比例是1−h：

| 变化 | 剩余输入比例 | 剩余输入相对减少 |
| --- | --- | --- |
| 80→85% | 20→15% | 25% |
| 85→95% | 15→5% | 66.7% |
| 90→95% | 10→5% | 50% |

这是工作量代理，不能直接推出3倍吞吐。举例：若85%时可缩减的prefill部分只占总时延30%，且该部分理想降为1/3、其余不变，总时延为原来的0.7+0.3/3=0.8，即约1.25倍速度；若排队也变化，结果又不同。该算例不含现场测量，也不是性能模型承诺。

本轮找到高度相关出处：[Netpreme/LMSYS文章](https://www.lmsys.org/blog/2026-06-27-netpreme-xmem)，页面标2026-07-08（URL日期不同）。文中95%讨论使用64K输入、prefill并发8及次级KV搬运；附录实测为H100级GPU、Qwen3-30B-A3B FP8、禁用GPU前缀缓存以测L2命中。它说明**缓存位置和搬运带宽可能改变瓶颈**，不证明HBM本地命中、当前GLM、V100或所有并发存在同一阈值。另[Character.AI 2024报告](https://blog.character.ai/optimizing-ai-inference-at-character-ai-2/)中的95%是其长对话和亲和路由下达到的命中率，并非相变阈值。

[NanoFlow OSDI25](https://www.usenix.org/conference/osdi25/presentation/zhu-kan)讨论许多常见端到端负载仍算力受限，提醒我们不能用某个attention阶段的内存特征替代全链路判断。后续拐点研究应在同模型、精度、硬件、输入/输出、到达率/并发及缓存层级下扫描h，观察prefill、KV搬运、队列、TTFT/TPOT和goodput，比较平滑与分段拟合并报告区间；采样稀疏时只展示曲线，不输出“拐点95%”。

## 5. V3-03/07：行为画像、群组与网关分词

至少保留三种相似性，分开输出：资源相似（输入/输出/突发/并发/服务曲线）、前缀亲和（同共享域下真实Token前缀重复）、业务语义相似（任务/质量约束）。同长输入的两家用户可能没有一个可复用前缀；同业务用户可能分别是短提取和长批处理。

[ServeGen v3 §3.3](https://arxiv.org/html/2505.09999v3)在其生产负载中发现部分大客户行为相对稳定，客户流量权重变化会改变总体分布。它支持按用户拆分观察，不支持每个用户都稳定或高斯。[2026-09的一年轨迹研究](https://arxiv.org/abs/2608.13573v2)也研究用户×模型演化；这些是有日期的实例，尚不足以证明“2026下半年整个infra行业转向”的趋势强度。

先用分位数、直方图、经验CDF、IQR/中位数、尾部占比、时间窗漂移与样本数表征，不拟定高斯先验。低样本/多峰/跨版本进入未知或混合组。群组必须在时间留出窗验证稳定性，新增业务、模板变更、输出尾部和突发都可触发失效。分组可减少运营配置数量，是否值得按组放置需与纯负载均衡、前缀亲和分别对照。

网关分词可研究三条路径：复用已可信计算的Token数/Token序列（身份与协议一致）；模板固定段预编码、变量段精确处理（注意边界分词不保证可直接拼接）；粗画像先选候选池、边界请求走精确分词。后两者只是待验证策略。P99估计长度加安全量并非上下文上限保证；必须保留可信硬上界或推理前精确校验，并为输出预算预留空间。估计失准、模板漂移、未知类型回退现有精确路径。

只可能省去重复的网关工作，不能假定推理端无需tokenization。净收益须计入画像查询、特征计算、误路由、重试和兜底开销；如网关本来不分词，这项优化直接不适用。共享实例仍保留租户隔离；[vLLM缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)的cache_salt说明共享域需显式管理，不能因聚类而跨租户合并缓存权限。

## 6. V3-04：压测代表性与实例配比

8K观察首先要明确是输入P、未命中C、模板前字节还是上下文规格名，以及请求占比和时间窗。保留三种权重：请求权重决定常见体验，Token权重反映输入量贡献，时间权重反映持续负载/峰时；有服务时间后再增加GPU时间权重。

配方应保留联合关系：输入、输出、重复前缀/命中、appid/模板、到达序列、并发限制、工具调用轮次、失败重试与长尾。随机重排会破坏缓存和突发；统一32K/64K也可能改变prefill/decode比例。长尾和峰值独立保留为压力配方，不能因主流约8K而删掉。

[BurstGPT v5](https://arxiv.org/abs/2401.17644v5)展示生产突发与会话/长度的复杂性；[vLLM bench serve](https://docs.vllm.ai/en/latest/cli/bench/serve/)提供到达率、突发与预热控制，但生成器参数存在不代表真实配方成立。首版输出配方与代表性差异向量：各分位数误差、分桶总变差、联合桶差异、尾部覆盖、分窗峰均比、重复距离和冷/热启动条件；不掩盖成单一总分。

实例配比必须等待同硬件、精度、模型版本、并行度、调度和SLO下的实测服务曲线。可用约束形式是最小化Σn_j·成本_j，满足各群组/峰窗的TTFT和TPOT达标、容量及隔离约束，并预留故障/误差余量。32K/64K/128K是上下文限制还是独立配置池需先核实，不能把规格名称直接当吞吐能力。现在交付实验矩阵和可行域条件，不输出具体台数。

## 7. V3-05：数据质量与协议审计

质量按用途判定，而非给整批数据一个可信标签。原始数据可追溯、字段合法、模型/模板一致、请求可关联、引擎语义校准是不同维度。字段合法只证明可参与某些统计，不能证明cached真实性。缺失与冲突要有原因、范围和影响，保留原值。

最低检查包括行数守恒、JSON/类型/单位、负数、cached>prompt、时区、截断、重试/重复、模型注册映射、Tokenizer/Template身份、请求ID可关联性。对cached全等prompt或长期不变只能报异常模式，不能直接指控虚报。注册协议需形成“源字段→映射→入库→指标”的证据链，区分计费缓存、lookup命中、成功加载和实际跳过计算。

缺失率低也可能集中在长请求或某实例。展示有效子集命中与缺失构成；若所有请求P已知且计数同口径，可给逻辑范围：已观测缓存总量A、缺失请求输入总量M、全部输入总量T，则全量报告命中落在[A/T,(A+M)/T]。P未知或语义未核验时不能给该范围，更不能称物理命中范围。MA paired指标只在两侧同时有效的集合上比较，另列独立指标和丢弃比例。

## 8. V3-06：全局与实例差距的可识别分解

先固定同一S、同一Token序列/算法/时间、相同共享授权和预热历史。定义G为忽略实例分配的理想可复用Token，R为按真实实例分配回放的理想Token，A为同集合引擎确认实际复用Token，P为共同输入总量，则：

`(G−A)/P = (G−R)/P + (R−A)/P`。

第一项可标“逻辑分片机会损失”，第二项是“实例内理想与实际残差”，不能自动全归因容量/驱逐。后者还含并发时缓存未完成发布、重启/失效、统计误差、调度与模型近似。相同容量无约束和可用历史条件下可验证G≥R；跨共享域、时间语义或缺失观测不满足前提时，连非负性也不能强求。A>R应保留差异调查，不静默截0。

当前用户理想按租户隔离、MA按制品/UUID，Trace与MA数据源不同；已有两个汇总不能直接填G与A。可优先在MA同一请求集合计算G/R候选，但这是未来新增能力，且G共享域须由现场策略确认。没有appid/授权映射就仅给可比性缺口。当前逻辑回放即时发布、无限账本，无法把高并发下未完成prefill的等待模拟为真实命中。

[SGLang官方实现 main](https://raw.githubusercontent.com/sgl-project/sglang/main/sgl-model-gateway/src/policies/cache_aware.rs)在本次读取中用字符前缀近似索引，且不平衡判断结合绝对和相对阈值后倾向轻载节点。这说明“路由器估计匹配”也不是引擎Token命中。调参需先核现场版本与参数含义；建议比较当前策略、负载均衡、纯亲和、带负载回退的亲和，不照搬该实现默认值。

[CacheRoute预印本 §5.3](https://arxiv.org/html/2608.19677v1)提供有用反例：复用收益小的负载中，亲和引起的偏斜可抵消收益。其半合成/特定硬件实验不能证明企业现场收益。离线仅有缓存账本时可报告复用代理、分配偏斜与重映射成本；缺少服务曲线和队列轨迹时不承诺TTFT/吞吐。

容量/SSD继续不作主线；保留占用、驱逐、失败分配、重启、驻留时间和工作集线索。一旦出现高驱逐且损失随压力变化，需重新审视“容量暂够”，不自动开启容量实验或SSD实现。

## 9. 低潜力场景的SLO与准入建议边界

当前源码 `user_monitoring/estimator.py` 从目标T、固定W、K、τ计算可容纳chunk和P90长度的所需命中参考。τ是用户参数；改变K不自动缩放τ。这个能力可以保留，但其逆向计算同样不产生真实排队模型。

在已获得每请求可靠P_i/H_i时，构造C_i=P_i−H_i，再计算情景值 `t_i_ref=W+τ·ceil(C_i/K)`；严格/非严格比较和C=0下必要计算/缓存读取限制必须沿用既有定义。总体h不能替代h_i，`Q90(P·(1−h))`通常不等于`Q90(P)·(1−总体h)`；等待与计算分位数也不能相加。

“目标T允许多少等待”可在固定情景下输出预算 `W_budget=T−t_compute_ref`，负值表示该情景无余量，非负只表示必要预算可能存在。无τ校准时只做敏感性表；W混含网络/排队/调度时，不能把预算全称排队上限。

可靠准入率还需到达、入队、出队、prefill/首Token/结束时间，调度/批处理策略、服务曲线、失败/重试、输出分布和硬件配置。Little定律只能用于稳定状态均值一致性核查，不预测P99。限流可能把等待移到调用方，也可能增加拒绝与重试；评价需同时报接受率、拒绝率和端到端体验。[DistServe](https://arxiv.org/html/2401.09670v3)以TTFT/TPOT约束下goodput为目标，其A100实验与经过校验的模拟不能替代本项目标定。
