## 1. 已核实的问题及责任

读取现有编译验收服务的ready报告73e1e977-84ad-4094-9fc9-8a91df746157：6条合成请求产生15个L1和15个L4 finding；其中只有一个代表性L1 finding关联到合格full实验，完整评估范围6条、实际修改6条。前端逐finding造卡，把其它14个L1及15个L4归入差异区，形成29张卡。

因此29是成对观察记录数，不是29个独立可行动问题，也不是29条受影响请求。代表性finding用于实验关联，不能直接当产品展示单位；同一解决方案也不能按rule_id随意扩散到所有finding。前端未建立“同一问题/同一修改方案”的业务聚合，导致重复和噪声，这是前端方案与实现的缺陷。

Token每fragment生成卡片，并优先取finding_candidates[0].title；后端通用候选标题“内容修改待业务确认”因此覆盖了T1–T4的业务类别。多个规则/内容位置混在同一请求卡片，也削弱了问题与建议的对应关系。规则映射已有基础，不能归咎于后端没给标签。

“修改方案与评估身份”直接展示Plan，“位置、规则与版本”直接展示原数据JSON，业务语义被技术字段淹没。大段全文与可选技术内容过多，卡片收益反而不突出。复制CSS和测试通过不足以证明与DEMO的产品表达一致。

## 2. 新的统一信息结构

展示单位改为同一业务问题及其具体修改方案，多个请求/多个例证作为这张卡的影响范围和证据，不再一条finding或一个fragment直接生成一张卡。同规则可能有不同方案，不强制每个探测器只能一张；相同方案重复观察只展示一次。

卡片：业务问题标题 → 影响请求数与比例 → 该类分析的预期提升 → 一句话修改方案 → 查看证据与修改方案。

详情：先看影响范围与收益摘要，再看相关差异/上下文，然后具体改法及修改前后示意。必要限制写成对应方案的一句业务说明，不铺设技术参数区。前台移除完整请求展示、Plan JSON、原始元数据JSON、版本/评估身份/内部路径控件。技术追溯仍留在后端成果与研发材料，不删除原始证据。

探测器类别数量和说明继续默认折叠，不放进主内容争夺注意力。保留现有通知后读取、不轮询、partial保留旧报告、历史固定选择及返回定位，不恢复参数、授权或评估表单。

## 3. 低命中率分析

### 主列表与门槛

取消“发现的差异”主分区。仅展示有具体方案且全范围评估满足既定严格>1个百分点门槛的优化建议；未评估、无可用方案、未达阈值的观察不在业务主列表展示。不能把“未评估”说成“收益低”，没有展示项时显示“本次没有达到展示条件的优化建议”，不写“没有问题”。

按方案/精确适用范围归并，同一个L1优化方案不再同时出现一批未关联实验的L1差异卡。聚合身份与关联由后端给出或依据完整明确的同Plan引用建立，不能仅按L1–L5代码粗暴合并。L4等仅有无可靠关联的事实不再用卡片占位。

L1–L5统一按“问题→具体方案→离线收益→展示门槛”设计；但当前实际能力并不齐全：L1/L2及可变换L3已有自动回放，L3集合变化部分、L4/L5当前无自动recipe/收益。需低命中后端明确各类可生成方案的条件、收益生成和不能量化的原因，不由前端伪造。没有可靠关联时L4不能把不同会话的正常变化写成历史污染；L5要先确认规范化确实保持业务语义。无成立条件时不展示，不保证每次五类都有卡片。

### 指标

低命中主卡与业务详情只展示命中率修改前→修改后及提升的百分点，不展示输入/计算Token变化。以同一报告选定范围的完整回放为口径，不拿小样本冒充全量，也不平均逐请求命中率。

建议“影响请求”明确为**本方案实际需要修改的去重请求数**，展示“影响N条 / 本次分析M条”。已有完整评估的modified_before.n/modified_after.n可提供修改请求子集计数，before.n或报告scope为同范围分母；本次实际例子可表达6/6，不必等待泛化affected_count才有数量。后续后端在推荐摘要中固定计数及其口径。发现观察数、证据请求对数量、位置数、操作数均不能替代请求数。

缓存收益可能影响未改的后继请求：收益仍取完整范围，直接修改请求数不冒称覆盖所有间接受益请求。若产品另需“包含该问题的全部请求数”或“实际收益变化请求数”，后端单独提供并命名，不能混用。各方案的请求范围可能重叠，不跨卡片相加。

### 证据

- 工具差异：只展示涉及的工具定义/工具字段及必要上下文，不展开所有tools。
- message差异：只展示相关message，必要时少量相邻消息，标明角色/消息序号。
- 动态内容：只展示变化片段及前后少量原文，高亮变化，不展示整条长system提示词。
- 大字段/64KiB请求：默认局部片段，按“展开更多上下文”逐步增加同一相关字段的上下文；不要求用户滚动完整请求。省略边界明确可见，不冒充完整字段。

“请求间差异证据”和“建议修改前后示意”必须分别标明。两条真实请求A/B的差别不是已经执行修改的before/after。

后台仍可保存完整原文用于校验。当前全文GET可以作为前端提取依据，不强制立即新增全文接口；优先使用可靠结构路径/位置和原文字面量范围。原始片段不能通过JSON.parse后重序列化损失大整数、空白或内嵌结构；没有可靠精确范围时仅显示已确认字段上下文，不用全文首次substring伪造高亮。缺少动态片段范围时由后端补证据引用或片段，而不是猜测。

## 4. Token异常分析

### 类别与问题标题

固定显示用户已定义的类别：T1 工具定义、T2 工具返回内容、T3 重复内容、T4 历史工具结果。类别标签与具体问题标题分开，不再以“内容修改待业务确认”作为卡片标题。

卡片按规则下的具体问题/修改方案归并，正确关联Observation/Unit/Location；一个fragment包含多个规则时不能拿首个finding标题代表全部。T2/T4共享内容位置不得重复计算规模，同请求多位置去重成一条请求；没有Finding的T3可以从Observation生成问题证据。

具体标题描述已证实的问题/方案作用，不能仅因为存在工具定义或内容很大就断言异常。纯inventory不作为“已发现异常”的方案卡片；明确方案依据不足的事实不再铺满主列表。

### 指标

显示影响请求N/M，以及同一明确评估范围内的：

- 模型输入Token：修改前→修改后、减少/增加量及比例；P为主。
- 计算Token：修改前→修改后、减少/增加量及比例；C用于避免输入下降但计算反升被包装成优化。

这两行都写业务名称，不只写P/C。不再把命中率作为Token建议的主指标；字节、字符、重复次数只是证据，不能冒充节省Token。总量与单请求平均不能混用。零/负结果不改写为成功；“输入下降、计算上升”明确提示取舍。不套低命中>1个百分点门槛、不把各独立建议收益求和。

### 自动收益前移

用户补充：“实际上初始 Token 分析可以自动产生量化收益，只是被我暂时放在V3了，如果你认为本次就需要展示，可以把实施计划提前。”

本线建议并据此将满足当前展示所需的最小后台链路纳入本轮返工计划：**后台生成明确方案→在离线副本应用→同范围回放→把建议/影响请求数/收益/证据关联保存到本次报告→完成通知后只读展示**。前移不是宣称当前已实现，也不需要用户逐卡填参数。

复用[Token自动建议讨论稿](../../length-analysis/AUTOMATIC_RECOMMENDATION_EVALUATION.md)的已有分析：T1明确模板、T2明确字段/条目规则、T3真实引用或删除约定、T4明确保留与替换规则。完整依据的场景先形成全链路，缺依据的场景需后台给出明确限制，不伪造授权、引用地址或业务无损性。可解释假设方案是否启用、具体保留档位/模板是后端补充设计中的待落定项，不因前移整个方向就自动批准任意裁剪策略。

自进化Agent、实际线上修改、自动穷举组合、全历史评估反查不随之前移。本期新报告内建立推荐与评估关联即可；旧报告不得在页面打开时自动重算。

## 5. 前后端分工和实施顺序（返工方案）

| 顺序 | 负责方 | 输出与验收重点 |
| --- | --- | --- |
| R0 建议摘要与字段对齐 | 低命中/公共后端、Token后端分别回传 | 一张方案的稳定身份、规则/问题、影响请求数及分母口径、全范围收益、证据/修改前后关联、可展示状态/原因；版本化扩展，不静默改冻结Schema |

| R2 小规模代表场景视觉确认 | 异常分析前端 | 保留UI-03配色布局，先核对少量明确卡片：低命中合格方案/无达标、T1–T4、Token输入下降但计算增加、局部差异证据；不以几十张重复卡填充评审 |

| R4 重新验收 | 前端与两后端，最终用户 | 真实代表性报告核对数字和截图；重复记录不增加卡片/请求数；局部证据准确；不含业务表单/POST；功能测试与用户表达验收分开 |

R0所列是数据语义要求，不是声称已有新API。已有modified_*计数和收益能够复用；缺少聚合身份/当前报告关联/精确片段的地方分别补齐。不以“字段不够”为由再做一个没有重点的界面。

前移方向已获用户本轮条件授权且本线明确推荐，无需重复询问是否需要自动量化收益。具体假设策略、T3业务依据、L4关联来源等不能代用户虚构；后端先形成可审查选择和已有配置来源，仅将确实需要业务决定的点提交用户。本轮尚未发送新后端prompt，也未启动这些session的实现。
