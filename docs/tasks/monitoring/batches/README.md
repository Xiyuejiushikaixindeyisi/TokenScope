## 每批必须有的文档

| 文件 | 写入时点 | 最小内容 |
| --- | --- | --- |
| CONTEXT.md | 开始前 | 设计/契约版本及摘要、上批闭环、相关源码/依赖、阅读边界 |
| PLAN.md | 写代码前，变更时更新 | 代码开发方案、行为/文件范围、门槛与验证命令、回退点、实施授权 |
| ISSUES.md | 发现与修复时增量记录 | ID、复现、影响/阻断性、根因、修复、验证证据、状态；没有问题也写“未发现” |
| TESTS.md | 每次实际验证后 | 输入/代码/资产/配置/环境身份、命令、时间与退出码、预期/实际结果、失败/复测、日志链接 |
| RESULT.md | 闭环时 | 按计划逐项说明实现和门槛；问题闭环/遗留项理由；准确回退办法；是否可进入下一批 |

计划与实际执行分开记录。不能用“已测试”“应该能用”替代命令及结果；不能删掉失败历史只留下最后一次成功。较大日志放 `artifacts/validation/monitoring/<batch>/`，本文档中给摘要、清单与链接；生产请求正文不复制到一般日志。

## 状态和门槛

`not_started → implementing → verifying → closed`；若缺少外部输入或验证失败而尚未修复，记录 `blocked` 及阻断原因。状态是研发记录，不自动控制 Codex 会话/goal。

进入 `closed` 必须同时满足：本批约定能力实现；必需测试通过且证据可复核；没有影响门槛的未决问题；静态检查/相关回归通过；RESULT 写明设计符合性和回退点；本索引、ENTRY、CODEMAP 与监控记忆均已更新。确实不影响门槛的遗留项也要给出理由、后续批次和验证方法，不能把必测项降格为遗留项。

每次阶段性进展、重要问题和每批闭环，都增量写入 [memory/tasks/monitoring.md](../../../../memory/tasks/monitoring.md)。CURRENT 只保留短状态与入口，SESSIONS 只改 Session 1 状态，不覆盖前端或其他会话。Git 尚未建立时用文件清单/摘要追溯；后续若有 Git，增加 commit 身份，不假造版本。
