# 低命中后端设计修订：手动入口、动态字段候选与两阶段评估

版本prefix-design-0.2，2026-10-31。用户本轮决定覆盖prefix-design-0.1、DESIGN_REVIEW及产品v0.4中不一致条款。A/B/C/D技术方向已确认；用户另明确：门槛是绝对提升严格大于1个百分点，低命中优化卡片设门槛，L4/L5差异证据与Token报告独立。只更新设计，不编码。公共契约更新为analysis-common-draft-2；正式Schema和实现仍未完成。

## 1. 检查发现及修正

| 原方案问题 | 修正 |
| --- | --- |
| 把业务用途未知当作禁止提出删除候选/做实验的理由 | L1/L3允许对有实际变化证据的动态时间、路径、标识等自动生成准确删除候选并离线评估；是否上线由业务决定。不再要求先证明业务无损 |
| 只给差异或笼统优化建议 | L1–L3具体方案先小范围评估，通过后再目标appid全范围评估，分别给出实际ΔR |
| 分析和评估均需零散手动触发，未表达两方向先后 | 用户一次提交appid、异常原因与对应显式开关；本次诊断任务按固定阶段驱动已确定方案的小范围及全范围评估，随后启动Token方向 |
| 全量、置信度、前端门槛含混 | 全量仅指该appid/服务/源run/选定窗口全部有效请求；高置信度限定为离线缓存改善，不保证业务正确；前端优化卡片严格ΔR>1pp |
| L4/L5只有局部block证据 | 提供两条完整请求JSON对比及差异路径；不要求收益，放差异证据区域 |
| 公共类型没有接纳Token线具体协议 | 接纳六项细化，并纳入TA-C0.2的受保护外层替换、三层证据身份、静态插件方案；不新增Token规则 |

## 2. 手动入口与方向开关

现场顺序：先由既有用户监控和MA监控产生结果；用户查看并向华为机Agent指定appid、异常原因；Agent选择明确源run/服务/窗口提交诊断。不由阈值、告警或自动采集启动，不把MA全量计算加入诊断任务。MA可以作为人工发现异常的背景证据，诊断输入仍为可解析的用户请求源；缺少可关联用户源则提示输入不足。

提交逻辑字段：source_selection、appid、reason_codes、reason_note、enable_low_hit、enable_token_content、evaluation_policy=screen_then_full。原因集合支持low_hit、request_length、qps；至少一个原因，保留用户原判断文字。未知原因不能猜方向。

| 用户原因 | enable_low_hit | enable_token_content | 阶段顺序 |
| --- | --- | --- | --- |
| 含low_hit，包括同时有长度/QPS问题 | true | true | 低命中探测→小范围→合格方案全范围→Token内容分析 |
| 仅request_length和/或qps | false | true | Token内容分析 |

原因和开关不一致时明确报参数冲突，不静默改变用户选择。开关是显式路由，不在GET时启动工作。低命中方向无发现、partial或规则失败不等于取消Token：方向终态后继续Token；共享源损坏阻断整个任务，用户中断则不再继续后续阶段。全范围候选评估待执行时不提前并行启动Token。

QPS只是用户选择Token方向的原因；首期内容分析不承诺查清QPS/Loop原因。请求长度均值≥32k、理想命中率<70%可记录为调查理由，不内置自动告警或判定“必然编排错误”。技术依据：缓存复用需要此前存在相同前缀；独立长文档的一次性请求可很长但少复用。[DeepSeek说明](https://api-docs.deepseek.com/guides/kv_cache/)支持前缀复用机制，不将其当前服务算法移植为本项目算法。

## 3. L1/L3删除候选与评估

L1区分已知cch元数据与普通动态业务字段；区分只影响结论标签，不妨碍建议删除和计算收益。L3工具description、参数说明等可混入路径/时间/执行标识；具有变化证据和明确位置即可提出清除这些动态片段的候选。不要求先确认权限或工具业务语义。

动态识别至少保留两个可比请求、同位置变化、稳定上下文、实际输入参与证据；路径/时间的语法只用于候选召回，不能单凭字段名认定异常。定义可用性或模板参与未知时保持观察，尝试具体删除副本对照；一次无输入变化不能证明字段永久忽略。

候选必须具体：请求集合、JSON Pointer、解码文本范围/内嵌路径、原值guard、明确删除/替换结果、规则/处理器版本。整行包含动态路径时可生成删除整行候选，并展示删掉的完整内容；不能暗中改成“删除整个prompt/工具集”来追求高命中。字段删除不满足原请求结构时改为明确合法文本替换或报告不可评估；不绕过原协议校验。

例：工具description为“读取指定文件。运行目录：/tmp/agent/job-71”，另一请求为相同说明及job-89。候选删除准确的“运行目录：…”片段，保留工具名称、Schema及其他说明；对窗口内匹配该规则的位置逐条应用。位置、被移除文本及作用范围均可审查。若路径存在于Schema约束/实际调用参数，必须独立列出准确变换，不顺带删除；这也不构成自动恢复某历史定义/合并工具全集的授权。

action_class：已知误注入cch为business_information_preserving；一般动态路径/时间删除为hypothetical_content_removal，记录“可能改变业务行为，待业务决定”。该标签不阻止两阶段评估，不触发额外审批。只操作离线副本；线上是否删除、移位或改写由业务决定。计量收益不是业务功能等价证明。

## 4. 小范围→全范围评估

### 4.1 范围和计划冻结

先冻结全范围F（目标appid同源/服务/窗口），再为每个具体方案选小范围S。S默认取F内包含发现请求、前序对照及后续请求的一段连续记录序列，保留其间未命中规则的请求，不能只拼接“重复得最多”的请求。记录选择算法、依据、边界、请求键摘要及覆盖。S按时间和源序号确定性选择，不反复挑选窗口直到超过门槛。

S前后各用独立空账本；S原始命中率必须重算，不能截取F中的H当作小范围基线。小范围大小/预算经后续合成规模测试确定，不凭空设生产默认值。若可用数据不足以构成严格小范围，标sample_insufficient，不默认判高置信度；允许用户显式指定直接全范围评估作为独立例外，不能伪造已通过小范围。

小范围通过后，全范围应用同一个语义变换及版本，按冻结F解析全部适用目标，新增目标逐条校验guards。记录pilot_plan_id、full_plan_id及共同transformation_digest。修改规则/参数后必须新建方案重做小范围，不能沿用旧置信度。

### 4.2 计算与门槛

每阶段复用统一编码和缓存算法，保存before/after的N/J/P/H/C/R及变更清单。R=ΣH/ΣP，ΔR_pp=100×(R_after−R_before)。P为0则无有效R。使用未四舍五入的值判定，严格>1.0pp，等于1.0pp不通过。

| 状态 | 条件及后续 |
| --- | --- |
| detected | 有字段/输入差异与准确候选，尚未实验 |
| pilot_blocked | 目标/资产/编码/范围失败，无after，不继续该方案全范围 |
| pilot_below_gate | 小范围实验完成但ΔR≤1pp；保存数值，非高置信度，不自动全范围 |
| pilot_high_confidence | 小范围完整、基线校验通过、原结构合法且ΔR>1pp；含义仅为该小范围缓存改善已复核，进入全范围 |
| full_below_gate | 全范围完成但ΔR≤1pp；保存结果，前端不展示此优化卡片 |
| full_qualified | 全范围完整且ΔR>1pp；前端展示优化卡片及前后实际值 |

这是收益筛选规则，不是统计置信区间。不存在“通过小范围就保证全范围改善”。小范围报告必须明确是小范围收益，不按比例外推全范围；全范围结果称“该窗口离线预期提升”，不承诺上线达到相同值。

全范围包含未修改请求，计算后续缓存影响。任一选中目标失败则当前阶段blocked，不丢行发布after。零/负收益留在后台评估记录，不因前端过滤而删除；默认前端只给已达标优化卡片和非逐项的覆盖/筛选统计。Token报告及L4/L5完整请求证据不受此门槛限制。

组合问题独立处理：多个前置动态字段可能单改无收益、合改才改善。可对同组明确因素生成有界组合候选，作为独立方案先小范围后全范围；组合通过不把每个成员单项标高置信度，不穷举所有子集，不相加收益。预算停止保存未评估状态。

继续展示P/H/C：R提高可能来自分母减少，不保证C降低；卡片写明“命中率提升”与“未命中Token变化”，不能把R提高直接叫成本优化。只要达到用户门槛仍可展示，但不得隐去不利指标。

### 4.3 结果字段

新增reason_codes/reason_note、两个enable开关、stage_order、direction_status；候选action_class、removed_content_refs、transformation_digest；评估stage=pilot/full、scope_ref、selection_method/version、N及覆盖、baseline_origin、before/after、delta_R_pp、gate_threshold_pp=1、gate_operator=gt、gate_passed、reason；发现pilot_evaluation_id/full_evaluation_id、confidence_basis、display_eligible/display_reason。Token方向不自动继承低命中gate。

业务卡片构造示例（仅说明字段，无实测）：动态工具运行路径；小范围600条，R 61.0%→65.0%，+4.0pp；全范围10,000条，R 62.0%→64.0%，+2.0pp。展示完整变更前后请求入口、删除位置、P/H/C及“删除路径可能改变工具使用方式，由业务决定”。正式结果所有数值来自回放，不能填示例值。

## 5. L4/L5完整请求对比

例子见[完整JSON样例](FULL_REQUEST_COMPARISON_EXAMPLES.md)。每组是两条完整请求，不是两段block；保存两份完整原文引用、摘要、原请求键、差异路径及关系证据。UI默认可折叠，但必须能展开完整左右对比；展示截断时必须提示并支持完整读取。原文格式对比与解析结构对比切换，不能格式化后抹掉L5要展示的字符串差异。

生产实例不得用合成JSON冒充原始请求；原文不完整/源损坏时说明不可提供完整对比，不拼接补全。L4无关联时标“可比请求历史内容不同，关联待确认”；L5说明实际输入是否变化。两者不强制预期提升，可放差异证据区域。若未来有明确方案并完成两阶段门槛，同样可以生成优化卡片。

## 6. 公共契约与剩余事项

A采用显式异步/独立诊断库及现有Dispatcher/锁；B采用有限证据深查和本稿两阶段评估；C采用有界候选索引与透明覆盖；D六项细化已写入公共draft-2。已读取Token的TA-I0.2/TA-C0.2，主会话接纳三项协议方向；不代称Token已确认新的门槛/编排修订，不修改其私有文档或自动启动开发。

仍需工程落实：实际Schema/字段编码样例、预算与小范围大小校准、处理器注册/类型定义、完整JSON读取API约束、开发batch与测试。上述不是重新审批用户已确认的四项方向。本轮只文档修正，未运行模型回放或宣称示例收益实测。
