- 本机人工通过及独立交付/容器验证是既有事实；本轮新增的是华为报告与源码/算术一致性核对，不冒称远端独立回放。

## 1 六条clock：已明确的差异与剩余精度

它们是同类问题下六个转换签名，不是相同finding的简单重复。按补证，消息中clock之外的用户身份段和agent身份/任务模板不同，因此生成不同field_shape。消息logical_field为system，clock块索引和替换常量相同；模板内容差异才是这里的主要分组依据。

[src/prefix规则](../../../src/tokenscope/prefix_analysis/clock_discovery_v3.py:215)按recipe整体摘要去重；[clock_shape](../../../src/tokenscope/prefix_analysis/session_clock_v3.py:81)刻意剔除clock块内内容。因此补证把“不同clock值”列作六方案划分依据不准确：时间变化是发现条件，时间值本身不进入field_shape。不同LCP或不同示例对也不是独立方案的分组键。

补证中rec[3]/rec[4]都标同一用户、同一PPT任务，但没有提供完整field_shape或逐字符diff，只有不同摘要前缀。可以说存在不同模板签名，不能声称已定位这两个模板具体哪几个字符不同。V4宜展示业务模板/编号和位置，避免把个人姓名/工号作为领导汇报的主要分组标签。

证据excerpt的“27”“46”是两请求的聚焦差异片段，不是完整clock内容。实际修改是整个受支持clock标签内部替换为NORMALIZED，保留标签与外部文本；不能宣传成只改了秒数。[例证实现](../../../src/tokenscope/analysis_common/sample_evidence_v3.py:73)对before/comparison与before/after分别裁取差异上下文，显示片段不等于完整修改范围。

## 5 stopped为什么不等于没有结果

BUS01字段：discovery.complete=false；cause_groups按L1=6、L3=56、L4=128，总190；reason为CAUSE_EVIDENCE_TRUNCATED；forced_termination=false；七项窗口complete=true；报告evidence_refs=10。

固定源码在新cause组且对应rule已达128时，设置discovery.complete=false并跳过该新cause组；继续后续配对/方案处理。[最终状态](../../../src/tokenscope/analysis_common/clock_worker_v3.py:209)同时检查未完成window和discovery.complete，所以即使已有七项评估完整，任务仍是stopped。不可改写原状态为completed，也无需据此把已有数字抹掉。

| 层次 | 本轮判断 |
| --- | --- |
| 全量业务/全部原因穷尽性 | 没有证明；样本有界且L4原因分组保留受限 |
| BUS01已发布七项窗口评估 | 补证及数字支持完整 |
| BUS01/ICSL已发布示例 | 补证支持可读；各有10/4引用，不再是0 |
| 其他五任务stopped根因 | 报告统一称L4上限，源码机制支持；仅BUS01嵌入了完整按规则分组数，本轮不扩称各组均有同等粒度原始审计 |
| 强制终止/OOM | 本补证六组均称forced_termination=false，无证据表明stopped由OOM造成 |

补证“810次L4访问−128组=682遗漏发现”不成立。通道访问计数、去重比较、原因分组是不同计量；同一组可来自多个请求对，同一对可能跨通道访问。不能相减得遗漏数，也不应据此直接扩大上限。达到上限的证据与超限后跳过新组的代码可以说明非穷尽，但不能量化漏掉多少业务问题。

## 6 原始报告仍有的审计限制

补证核心疑点已解决，剩余不阻止有界单方案能力的技术阶段收口，但不能被写成不存在：

- 只给任务/报告/转换SHA前缀；recipe“完整字段”实际含省略号，未提供完整六模板差异；同名PPT两模板字符差异未核清。
- 用12条示例代替实际修改集合，未提供plan/rows交集；不支持组合收益或无冲突承诺。
- clock片段不等于完整替换范围；不同clock值不等于不同recipe；self_evolution数量在文字/表格间不一致。
- 样本限制应解释为Token预算；review_requested=false，不是跨窗口验证。
- L4访问次数不能减组数；负收益的Token方向笔误已纠正。
- 报告命令仍含Markdown链接格式，不宜复制执行。源码片段和数字可核对，整篇不是原始JSON完整封装。

不要求为这些文案/证据精度问题重新跑全量。后续需要精确模板差异或组合覆盖时，先只读现有产物；需要新能力才按V4审批实施。

## 7 更新后的V4规划建议（不是开发派单）

### P0 汇报与结果解释

保持已批准V2四入口及L4/L5，优先在现有卡片中解释“问题类别→模板变体→修改范围→单项收益”。同类clock汇总成一类，子方案保留模板/消息位置、匹配修改数和before→after，不机械合并/删除不同recipe。不在标题里堆规则名或个人身份信息。

可见区域明确四项：实际N/父集；单方案收益不可相加；样本内实算而非全量/独立验证；时间固定化业务风险。呈现“已完成的方案评估”和“原因覆盖受限”两种状态，不能用stopped一个词覆盖全部事实，也不能把后端stopped隐瞒改成完全成功。L4仅保留代表性原因/例证的统计定义需先设计，不直接把128改大。

汇报可用证据：ICSL合成102条35.95%→90.16%；真实BUS01选定73/1047样本，单项最高31.93%→43.27%（+11.34pp）。其余单项可按报告来源引用，不能讲“整体提升30%”。保留BUS02负收益作为筛选不适用方案的证据。结合输入P和计算C变化解释路径删除，不把微小分母变化包装成显著业务收益。

组合方案是明确新增能力，非单纯卡片求和。若用户需要，先构建操作位置与请求交集、互斥/叠加关系，再对联合计划做同样本一次回放；需求未批准前不实施。当前缺少组合收益不阻断V3。

### P1 模型演进

按用户目标Qwen3.6→3.8、GLM5.2→5.3、DeepSeekV4→V4.1规划；本轮不声明目标官方资产已取得或兼容。固定实际规格/制品别名、Tokenizer/Chat Template revision与SHA、模式/协议/块参数、MA映射及新TTFT chunk_seconds。旧模型和成果只读保留，新模型独立身份，不能重命名旧结果；相同CSV换编码的离线对照不能冒充新模型生产观测。

新模型首轮小样本跑通计量/前端/资源边界，再按明确授权放大；历史Qwen全量约30.3GB/32GB是资源风险，不凭新名字认为可直接全量运行。新TTFT参数未提供时标待配置，不沿用旧秒数冒充标定。

### P1 Token工具异常

从真实业务的单请求JSON重复载荷、跨tool消息完全相同结果、单次巨大返回切入，先复用既有T3提取/精确重复/父子重叠去除与T2体量能力，验证真实样本缺口，不默认从零重造探测器。

输出要区分可证明的重复/体量事实、需业务确认的删除/裁剪/引用方案和同样本实际收益。不能把不同请求携带的共同历史算成单请求重复执行，更不能据重复文本推断工具调用次数或无限loop。巨大返回要按工具/任务类别与必要字段评估，不能统一截断长度或只保留最近三条。

核心收益至少同时报告ΔP、ΔC及命中率变化；完整请求按真实模型重新编码/回放，字符/局部Token度量只能作线索，不冒充可兑现节省。检验业务任务质量、工具协议关联和证据定位。BUS02已实际证明“输入减少不保证计算Token减少”，应纳入V4评估样例。内存、样本准入及每方案资源释放作为贯穿验收条件。

顺序建议：先汇报口径和状态/覆盖契约→固化模型接入身份，同时做工具真实样本研究→获准后开发→独立验收与版本交付。本轮不新建session、不发送开发任务，V4实现范围待用户/产品方案确定。
