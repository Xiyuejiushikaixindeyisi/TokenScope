# MaaS分流公开调研与TokenScope V4产品判断

调研日期：2026-11-14。责任：V4产品设计与汇报，实际session `01a1d3e3-0c34-7320-bf6f-14438c120aed`，本机环境复核。用户告知华为正在执行探索任务；本轮在等待回传期间研究公开资料，不改变已转发prompt，不生成prompt-3，不启动部署或修改HTML/PPT。

**判断：基于场景组织流量、减少可复用上下文被打散，值得作为试点方向；目前不能据公开资料认定“agentic/chat两类硬分池＋取消一切长度调度＋GB不看负载”就是正确生产方案。** 更完整的方向是：场景决定服务策略，真实会话/前缀决定缓存亲和，长度、队列、输出与缓存容量决定能否承载。下面分别列公开事实和本项目推断，未把厂商能力当华为现网事实。

## 1. 先区分分流所在的层次

用户进一步要求重点展开DeepSeek，见[长度调度、共享KV与独立MA边界](DEEPSEEK_ROUTING_AND_SHARED_KV_20261114.md)。该补充区分块KV、状态缓存与读取成本，并对照GB/GF/motor；仍仅做机制与条件判断。

| 层次 | 解决的问题 | 与本次讨论的关系 |
| --- | --- | --- |
| 业务/服务策略 | 哪类任务需要怎样的时延、输出、质量及复用策略 | agentic/chat可作初始标签，混合appid需要更细业务证据 |
| 同模型跨缓存域路由 | 请求送到哪个独立缓存池，如何减少重复prefill并避开拥塞 | 对应GB选择MA UUID，是当前主要问题 |
| MA内部P/D调度 | 哪个P处理输入、哪个D生成，如何分配计算和显存 | 对应GF与独立motor的内部职责，不能凭产品判断冻结其接口 |
| 跨模型语义路由 | 简单问题选小模型、复杂问题选大模型 | 不等于本次同一0731模型的MA分流；不能用它证明场景分池收益 |

同一业务可以具有多种请求形态；同一会话的输入长度也会随轮次增长。业务标签、上下文规格、前缀身份与缓存域是不同维度。

## 2. 六类对象的公开做法及原因

以下为截至调研日可访问的官方文档、作者论文和官方仓库材料。Mooncake是Moonshot/Kimi相关的服务架构与开源项目，NVIDIA是推理基础设施提供方，Qwen是模型系列；不将这三者都描述为具有相同商业部署形态的MaaS供应商。

| 对象与证据范围 | 公开做法 | 原因及可借鉴点 |
| --- | --- | --- |
| 火山方舟，API使用层 | 上下文缓存文档提供可选`prompt_cache_key`，帮助相同前缀的请求获得缓存亲和；实际命中看usage，不能凭请求成功或传了key认定命中。 | 客户端提供连续上下文线索，以减少重复输入计算。公开接口不揭示整个生产集群是否按agentic/chat分池。[上下文缓存](https://docs.volcengine.com/docs/ark/context-cache?lang=zh) |
| DeepSeek，V4.1 Flash官方部署Q&A | Prefill保留按上下文长度分档，并动态分配计算资源；独立3FS缓存存储使各prefill引擎可复用前缀，因而不依赖前缀亲和选引擎。 | 共享缓存使计算负载调度与缓存位置的冲突减弱；该V4.1说明不能套作华为0731的配置。[Data-parallel load balancing／KV cache storage](https://github.com/deepseek-ai/DeepInfer/blob/main/doc/inference_deployment_qa.md) |
| Mooncake，FAST 2025作者论文 | 全局prefill调度同时考虑可复用前缀、排队、计算与传输时间；热点缓存可复制，decode另做调度。 | 用共享存储及调度共同减少计算，目标是满足SLO的有效请求能力；并非无条件选择最长命中。[论文§4–5](https://www.usenix.org/system/files/fast25-qin.pdf) |
| 腾讯云，TI-ONE智能路由 | 各副本独立KV时，用前缀缓存得分及Token负载得分选择副本；先排除不健康或角色不匹配对象。 | 普通轮询会打散重复前缀，但命中与负载都需考虑。此为TI-ONE公开功能，不能外推为全部混元API的内部部署。[官方文档，页标更新2026-10-27](https://cloud.tencent.com.cn/document/product/851/140150) |
| 阿里云/Qwen相关平台 | PAI InferX依次考虑会话亲和、前缀缓存、负载；软亲和及前缀选择都可在过载时退让。百炼另提供Qwen上下文缓存API。 | 连续对话需要稳定落点，热点又不能压垮单实例。PAI策略不能当作百炼Qwen全量服务的未公开实现。[InferX配置](https://help.aliyun.com/en/pai/inferx-config-center)、[百炼缓存](https://help.aliyun.com/zh/model-studio/context-cache) |
| NVIDIA Dynamo，公开路由组件 | 按可复用KV与活动prefill/decode负载综合选worker；区分不同缓存层的价值，抑制缓存丰富但过载的worker持续吸流。 | 兼顾重复计算、解码压力和容量，而非只最大化命中百分比。[Routing Concepts](https://docs.nvidia.com/dynamo/latest/knowledge-base/modular-components/router/routing-concepts) |

这批证据支持“把复用关系引入路由”，也支持“按工作负载设置不同服务策略”；**尚不能证明上述供应商普遍只用agentic/chat两个标签完成物理分池**。文档未披露的部分记为未知，不推断不存在。

## 3. 对现有MA架构最有用的区别

本机[MAAS_REFERENCE](../../architecture/MAAS_REFERENCE.md)依据用户2026-10-30说明：同一MA UUID内P节点可共享缓存，不默认跨UUID共享；GB按模板前JSON计量分规格，而模型输入计量是模板后Token。用户本轮又指出跨MA可能存在物理隔离。这些是本项目背景，最新配置与实际效果仍等华为报告。

由此推断，若同一会话因长度跨档或普通均衡进入不同UUID，旧前缀可能再次计算；但必须有实际请求与缓存域的对应证据，不能只用用户理想命中率减MA理想命中率归因。

DeepSeek的对照说明：**长度调度与缓存碎片化并非必然绑定**。其共享存储条件使计算落点可变；现有MA之间若无此共享，改变落点的缓存代价就更重要。不能只照搬其中的长度档位或负载均衡方法，也不能由此推导应忽略长度。[官方Q&A](https://github.com/deepseek-ai/DeepInfer/blob/main/doc/inference_deployment_qa.md)

llm-d本身也提供前缀缓存、KV占用和队列等路由组件，以及KV事件驱动的精确前缀路径。用户观察到现网GB主要承担负载均衡，应保留为具体部署观察；不能归纳为“llm-d只能做负载均衡”。现网版本、启用策略和可见缓存域尚待核对。[llm-d配置文档](https://llm-d.ai/docs/architecture/router/configuration)

## 4. 对用户方案的逐项产品判断

下表是依据上述材料及本地架构作出的分析建议，尚非用户批准的实现规格。

| 用户设想 | 当前判断 | 需要保留的条件 |
| --- | --- | --- |
| 从纯长短标签转向业务场景 | 支持作为探索方向 | 标签应能解释请求之间的复用与服务目标；有混合业务的appid不宜强贴唯一标签 |
| agentic对应长输入，chat对应短输入 | 不宜作为分类规则 | 长文档问答可以很长，agent中的分类/工具选择可以很短。应结合输入/输出分布、前缀、工具结构、会话证据；无会话字段则保留未知 |
| 跳过32K/64K/128K固定分流 | 可讨论减少对连续上下文的切割，暂不能认定应全部取消 | 保留真实最大上下文、显存、SLO与排队约束；先区分规格是路由标签、服务承诺还是物理能力差异 |
| GB主要做KV路由，GF做内部均衡 | 方向合理，但GB仍需跨MA容量和拥塞保护 | GF只能在本MA内调度，无法替GB消除MA之间的冷热不均。可复用收益须与等待及重算代价一起判断 |
| 先按appid引流两个试点 | 适合作为可操作的流量选择入口 | appid是租户/产品身份，不等于一个会话或一种业务；进入一个MA缓存域也不等于所有请求固定到一个P节点 |
| 减少MA数、扩大内部XPYD | 保留为独立架构候选 | 缓存聚合可能获益，也可能增加排队、通信与故障影响；10P5D仍是示例，不能从路由论文直接认定为优选 |

这里更适合讨论的组合是：**场景服务策略 → 可承载且可复用的MA缓存域 → 考虑过载退让的会话/前缀亲和 → MA内部P/D调度**。这是问题分解，不规定代码模块、打分权重、调度算法或部署拓扑。

场景分池有收益的前提是能减少重复计算或不合理的资源竞争。若两个场景本来共享相同前缀，硬拆池反而可能重复保存缓存；若只换场景名称而流量仍随机散落，标签本身也不会产生命中。单个大appid固定到小池还可能出现热点与闲置并存。

## 5. 实践讨论提供的提醒

AIBrix公开文档将会话亲和用于多轮和并发agent请求，并在前缀路由中结合负载；它说明场景信息可以影响路由机制，但不是“给appid贴agentic标签就完成了调度”。[Agentic routing](https://aibrix.readthedocs.io/latest/features/gateway-routing/agentic-routing.html)、[Prefix-cache routing](https://aibrix.readthedocs.io/latest/features/gateway-routing/prefix-cache-aware-routing.html)

官方仓库的[讨论#2782](https://github.com/vllm-project/aibrix/issues/2782)报告：网关前缀文本曾遗漏tools，导致网关以为相同、引擎实际前缀不同；页面显示2026-09-28由#2784修复关闭。这是贡献者报告及处理记录，不是本机复现或华为缺陷。对本项目的启发是：评估缓存路由时，必须区分网关估计匹配与引擎真实KV命中；模板、tools和模型身份可能影响两者一致性。无需因此在本轮增加探测器或改造现场。

## 6. 如何把方向与业务价值相连

TokenScope目标沿用户决定：通过减少无效计算和改善KV复用，提高单卡任务产出。建议最终评价口径是**满足质量与业务时限的成功任务数／卡分钟**，并按业务类型分开；同一agent任务的多次模型请求不能重复计作多个业务任务。

当前若只有请求日志，可先报告成功请求数、SLO达标请求数、输入/输出量、真实命中及未命中输入、排队与端到端耗时。这些是阶段证据，不能直接改名为任务完成数或业务价值。卡分钟需覆盖所用P/D资源、明确硬件与分摊；不同硬件或业务混合比例不可直接比较。理想命中率是潜力指标，真实命中增加也不保证decode或业务完成更快。

现有四份探索prompt已经在提供必要的前置信息，无需打断现场追加全量监控：

- prompt-1阶段1：确认混合业务与规模，为appid标签可靠性提供依据。
- 阶段2：区分必要长任务和可治理内容，避免把长度直接当浪费。
- 阶段3：22个短低appid的输出分布，帮助区分短确定输出与长生成负载；双峰是线索，不能单独证明业务类型。
- MaaS prompt-2：两个试点独立/合计流量、规格与UUID分布及0731配置，支撑初步承载判断。req/s仍需与输入、命中、输出及并发结构结合。

等待报告后再判断两个DeepSeek-V4-Flash-0731试点（com.huawei.ucd.uiplus.wa、com.huawei.cloud.ioc.global）的场景是否集中、缓存复用是否被分流切断、目标MA能否承担其负载。数据整理和生产重放prompt-3仍待用户讨论，本调研不提前设定实验规模、SLO秒数、收益比例或部署方案。
