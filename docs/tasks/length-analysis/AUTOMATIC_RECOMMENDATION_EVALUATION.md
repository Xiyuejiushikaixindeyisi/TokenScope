## 1. 为什么当前初始分析没有收益

这是当前实现的链路缺口，不是Token分析在技术上不能自动评估，也不是产品必须退回前端填写参数。

当前 [plugin.py](../../../src/tokenscope/token_content/plugin.py) 生成内容事实与候选；[candidates.py](../../../src/tokenscope/token_content/candidates.py) 为候选保存parameters_json="{}"及missing_parameters。T1/T2即使存在适用业务策略，当前也没有把策略编译成完整修改参数；T4有retain_last策略仍缺替换内容；T3没有自动授权候选。

[service.py](../../../src/tokenscope/analysis_common/service.py) 初始Token阶段只保存fragment/index；prepare_mutation与evaluate_plan位于后续显式评估任务。已有 [transformations.py](../../../src/tokenscope/token_content/transformations.py) 对所有修改要求business_basis_ref，缺失则BUSINESS_BASIS_REQUIRED。前期实现具备“检测＋受保护修改＋公共离线回放”，尚缺“后台形成具体方案并自动接续评估”。此前接入回执描述了这个事实，但将其作为最终产品边界不符合用户目标。

正确边界是：**参数必须明确，不等于参数必须由前端用户填写；离线假设评估，不等于授权修改业务Agent。** 后台可从已登记策略、工具契约、确定性规则生成参数；无业务策略时可考虑明确标注的假设方案，不能伪称业务授权或无损。所有操作只作用于离线副本。

以下“可自动”均指补齐方案生成和调度后可自动完成，不表示当前已实现。现有评估器重放固定请求序列，不重跑Agent，不能证明修改后任务质量或未来工具调用保持一致。

## 2. T1–T4逐项判断

| 规则与场景 | 后台能否自动生成并评估 | 必要依据/限制 | 最小补充 |
| --- | --- | --- | --- |
| T1：已登记的工具description精简版本 | 可以；按工具定义摘要/版本与路径选择替换文本，复用replace_tool_description | 后台配置包含原定义匹配、明确替换文本及来源。不能只凭工具名匹配，不能用字符预算自动推导正确说明 | 替换模板/规则映射→完整参数与guard→公共回放 |
| T1：单条description内可机械识别的重复片段 | 可作为新增的确定性**假设方案**，自动生成差异并评估；不能自动声称无损 | 当前规则的identical_descriptions是多定义间相同描述，不等于具备单条说明去重能力。删除重复强调/示例仍可能影响模型行为 | 若纳入一期，限定重复模式、保留方式、例外与版本，增加候选生成；不是本轮已确定新增探测器 |
| T1：不同工具有相同说明，或某工具未见调用 | 仅凭这些不能生成可信的删除/合并方案 | 各工具说明独立生效，未见调用不等于工具无用；Schema、权限和需求不可猜。延迟加载改变后续执行，不可用静态删tools冒充改造 | 首期保留建议；有明确替换模板时走上一行。不新增LLM改写/工具搜索执行系统 |
| T2：已有允许字段/字段层级和工具身份约定 | 可以；allowed_fields/field_level可生成project_result_fields参数 | 当前policy表示允许集合。需明确它是否允许在模型输入中省略额外字段；检测约束不自动等于修改策略。工具输入Schema不能冒充返回数据契约 | 补策略→投影recipe映射及作用范围；原字段为空/异构行/类型冲突则阻断并给原因 |
| T2：已有明确的行/条目保留规则 | 可以；生成select_result_lines/items的start/end | 必须知道保留头部、尾部还是指定区间。仅max_items/字节上限不能决定保留哪部分；字节预算不能直接换算成行/Token数 | 保存选择规则并按当前内容长度生成合法区间；截断记录放允许的标记位置或外部变更清单 |
| T2：只有完整大返回，没有业务规则 | 可以提供版本化**假设裁剪方案**并自动算静态输入变化，但不称“业务确认收益” | 后台明确给出保留方式/范围及被省略内容；不能按debug等字段名猜无用，不能凭空生成摘要。具体假设档位需在后端方案中一次确认，不让前端用户填 | 产品/服务级有限recipe集合；生成完整差异和assumption说明，质量未验证。未批准默认recipe前不编造参数 |
| T3：下游已有引用协议及可信引用映射 | 可以自动替换、评估；用户不用逐次授权 | 精确工具版本支持该形状；每个载荷有真实引用值及业务可解析依据。出现document_ref字段不证明有真实对象或同内容映射；当前仅支持既有handler的有限Schema形状 | 后台引用协议/载荷→引用映射、适用工具与来源证据；复用授权派生及guard，不新建对象存储服务 |
| T3：额外普通消息副本已有可删除约定 | 可以自动选择约定中的副本并评估 | 业务约定限定角色、位置/来源、保留哪份及适用范围；完整重复事实不等于副本可删。必须保留协议和调用配对 | 后台有版本的删除授权规则，绑定本次证据，生成authorize_candidate输入；不是批量设置authorized=true |
| T3：仅有三处完全相同载荷，无协议/授权 | 默认只给重复事实及引用复用建议，不给可执行方案收益 | 虚构短引用或删除普通消息虽然能算出较低P，却不能称为可行的预期收益。已有批准产品明确要求引用能力/真实引用或删除依据 | 不要求前端补参数；缺口明确为协议/授权证据，交由后台策略维护。不得用通用裁剪假设绕过T3授权 |
| T4：已有保留K、作用域/单位及替换内容规则 | 可以自动生成历史结果替换并评估 | K区分结果容器/content part；替换摘要/引用必须已存在或有合法确定性替换规则。仅keep_last不等于完整修改方案 | retain_last策略→位置集合＋replacement_json；保留tool配对、记录实际覆盖；复用apply_retention_replacements |
| T4：没有保留策略或只有K没有替换规则 | 默认事实与建议；可另加明确标注的**假设保留方案**进行自动评估 | 假设K与替代内容来自批准的后台recipe，不能判断结果过期、不再需要；占位文本必须明确为省略，不伪称摘要或可重读引用 | 需确认是否纳入假设模式及有限档位/合法替换方式。是已批“必须业务K”规则的拟议扩展，尚未批准实施 |

共同结论：自动执行依据分三类——已有业务策略驱动、可解释的离线假设、缺少协议/业务事实而暂不可评估。不把第三类的所有缺口称为“缺参数”；也不把第二类的数字包装为已确认优化。没有安全可行方案时输出具体原因，而不是制造保证为正的收益。

T1优先采用已有替换模板；T2最适合先打通策略生成与假设裁剪；T3严格依赖引用/删除依据；T4完整策略可自动、无策略的假设模式需明确产品认可。纯粹数值上能对任意删除算ΔP，不等于可将其作为用户可采用的建议。

## 3. 最小后端补充：复用已有能力

### A. 后台方案生成及依据登记（Token侧）

新增有限、确定性的recipe解析/生成环节，把现有Observation、Candidate与后台配置转换为完整参数。配置可先使用项目内有版本的文件/服务配置，不新增前端表单或管理平台。匹配至少包含appid/模型服务范围、工具定义身份、rule、路径/内容类型、策略版本与适用条件；每次报告保存实际使用快照/摘要。

将“异常判据”与“修改方案”区分：limit决定是否超限，projection/保留区间/替换文本决定怎样修改。对可推导参数自动生成；对不能推导项记录具体缺口。business_basis_ref是来源引用，不应由系统编造一段“业务已同意”。

拟议增加typed basis：business_policy / offline_hypothesis / explicit_authorization及其引用、版本、假设、限制。不静默改现有冻结Schema；和公共维护方确定版本化扩展。当前handler一律要求business_basis_ref，假设模式不能仅把recipe名称塞进去冒充业务依据，需要明确的类型校验和允许范围；T3真实引用/授权检查保持。

### B. 初始任务中的自动评估编排（公共侧集成，Token提供方案）

原scope的Token内容扫描→汇总/去重相同recipe的适用位置→生成完整Plan→guard校验→已有evaluate_plan→记录成果→统一发布。沿用现有低命中先结束、Token分析原始scope的顺序；不以低命中修改后的请求作为Token输入，不通过前端POST或为每条候选自调用HTTP。

只回放选定appid及窗口、同一编码/配置身份与原顺序，不全历史回放。一个方案可以覆盖同scope中所有符合精确匹配的请求；不能只改一个样例后声称整个工具已优化。评估仍需遍历该scope的请求序列，不能只把被修改请求单独编码后忽略前缀命中变化。

复用现有离线副本、原值guard、原子操作、内嵌JSON编译和P/H/C计算；不放宽字面值/模型身份检查以制造收益。按request/位置/recipe/参数身份去重，T2/T4共用位置不重复回放；不同替代方案各自比较基线。只做独立方案即可，不要求自动穷举组合；组合收益继续独立评估，不求和。

预算独立限定候选/方案数、编码调用、请求/原文字节和执行停止；超预算保存not_run/partial及原因，不默默删发现。排序与截断规则需明确记录，不把大字节数量当精确Token收益排序。该部分可复用既有budget/RunControl，不另建回放引擎。

### C. 发现—建议—评估的只读关联与发布（公共侧）

当前Token初始报告无evaluation，discovery也不提供发现到全部评估的反向目录。最小方案是**在本次诊断成果内保存关联**，前端无需扫描其他历史任务：recommendation_id、rule/observation或finding引用、evidence refs、recipe及参数/依据、plan_id、evaluation_id、覆盖与未评估原因。

T3没有Finding时必须支持Observation引用，不能强制造Finding才能挂收益。已有Plan/evaluation/items继续复用；扩展报告内推荐关联对象，具体kind/版本由公共方确认，不在本稿声称已存在新GET。后台完成后由既有discovery通知前端读取，不轮询、不触发用户操作。

本任务扫描与自动评估完成/停止后统一封存。预先声明的不适用或缺业务依据作为建议状态；它们是否影响整体ready需在公共设计中明确，不能让“无可行方案”和“评估执行失败/预算未完成”混用。运行失败/覆盖不足沿用partial等真实状态，不能为成为默认报告隐藏失败。保持已确认的partial不替换旧默认。

不必为了新报告自动收益先补齐“所有旧评估子任务反查”。旧报告缺关联继续如实显示；若要求历史收益补齐再单独定义迁移/回填，不能页面访问时重跑。

### D. 前端只读消费

后台同时产出“改哪里、如何改、依据/假设、前后样例、覆盖范围、预期输入影响”。前端只显示结果与证据，无参数、授权、提交按钮。不得把有条件/假设收益与已确认策略收益混成一类，也不把“未评估”显示成0。

量化最少给before/after P/H/C及R、修改请求子集与全scope、基线/编码身份、status与reason。零收益、负收益、P下降但C上升保留，不套低命中>1pp门槛。明确这是静态输入回放结果，不能保证线上输出、质量、费用、TTFT或Agent后续行为。

## 4. 建议的最小交付顺序与验收（待审批）

1. 先打通“完整后台recipe→既有handler/Plan→初始任务自动回放→报告内只读关联”，以T2明确字段投影和T4完整保留策略验证；无需前端表单。
2. 接入T1后台替换模板、T3已登记引用/删除约定，缺依据时保留建议及具体原因。规则触发不要求用户逐次输入。
3. 再按产品认可的范围补T2假设裁剪、T4假设保留；T1机械去重是否纳入另在方案中明确。假设recipe的具体值与模板需确认，不设未经讨论的“行业默认值”。不扩为LLM自动改写、Agent执行或参数错配探测。

验收必须证明：没有前端POST也能从一次后台分析得到可追溯建议与评估；policy可自动编译、依据不足不会伪造授权；T3缺协议不生成假引用；原文/协议/数值guard有效；全scope与修改子集不混用；共享证据去重；预算/取消/失败可读；零/负收益保留；完成通知读取包含关联的封存报告；页面访问不计算。业务质量不在本期静态输入回放证明范围。

## 5. 需要确认的最少产品选择

用户目标已明确，不再询问是否需要后台自动收益，也不要求前端补参数。尚需在详细方案中落定：

- 是否首期接受带明确假设说明的T2/T4收益，以及有限recipe的具体保留方式/档位与替换模板；不能将假设收益默认标为已确认修改效果。
- 业务策略/工具引用及删除约定从哪一份已有配置或业务规范读取；没有则相应场景明确待依据，不阻碍其他可评估场景。
- 公共层报告关联扩展版本、自动评估预算及ready/partial语义。属于后端设计协同，不应由前端业务用户填写。

本稿纠正 [FE-R-T1](FRONTEND_READONLY_RECEIPT.md) 的产品收口理解：该回执的现有能力事实仍有效，但“只读界面可接受没有收益”不能替代后台自动建议与收益目标。下一步应先补这部分后端设计，前端按只读目标预留结果映射；本轮没有批准或实施这些补充。
