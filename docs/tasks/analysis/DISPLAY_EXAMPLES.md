## 2. 低命中页签

### L1 已知cch元数据破坏前缀

**卡片标题：** CC动态元数据进入instructions，建议清理。

**证据：** 示例窗口4个请求，4/4检查；其中3个具有更早可比请求。r1与r2在instructions首行分别带cch=a7754和cch=69cb1；后续稳定说明相同。字段到输入差异映射已核验。r1为对照锚点，不把它加到“3个前序对照发现”中。

**判断：** 已识别误注入元数据；业务信息无损清理。显示准确元数据行位置，保留其他instructions，不删除任意正文中的cch字符串。

**修改：** 本窗口4个请求中符合相同来源条件的首行元数据都清理，包括锚点r1。评估请求4，实际修改4。

**离线结果的构造展示：**

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 请求数 | 4 | 4 |
| P 输入Token | 16,384 | 15,872 |
| H 理想命中Token | 0 | 11,136 |
| C 理想重算Token | 16,384 | 4,736 |
| R 理想命中率 | 0% | 70.16% |

说明：本窗口输入少512 Token，理想重算少11,648 Token；命中率增加70.16个百分点。不是生产缓存或费用预测。示例可按B=128、MTP退一块构造：修改前各P4096、H0；修改后各P3968，首请求H0，后三请求各退块前匹配3840、H3712。该说明只用于样例算术自洽，不表示实际编码得到此长度。

**操作：** 查看字段差异、查看4条修改清单、查看同窗口评估详情。

### L2 工具排列不稳定

**卡片标题：** 工具定义未变，工具清单顺序变化。

**证据：** r10为[search, read_file, write_file]，r11为[write_file, search, read_file]；3个工具逐项定义和数量相同，输入前缀因此变化。展示集合核对结果与顺序差异，不只给“工具漂移”标签。

**建议：** 在输入构造时固定为[read_file, search, write_file]，保留工具定义和权限。

**评估状态：** 可评估，尚未运行。收益显示“—，待评估”，不是0；不要求先做一轮任务质量实验才能评估固定排序。

**边界反例：** 如果read_file的参数定义也发生变化，不把整个差异归为排序，关联L3。

### L3 工具定义内混入运行字段

**卡片标题：** search工具description每次带入不同request_id。

**证据：** 两个可比请求在tools对应description末尾分别出现request_id=req-a/req-b；工具其他定义不变，已核验该内容进入模型。来源约定证明这段是运行追踪元数据。

**建议：** 仅移出这段运行元数据，保持工具能力说明、Schema和版本。与L1共享位置证据和修改方案，不生成两份可相加收益。

**评估：** 可按准确字段/后缀规则生成副本；未运行则无收益数值。

**合法变更反例：** 若required从[path]变为[path, encoding]且有新版本记录，显示“工具版本变化”，不自动恢复旧定义。没有确认的替换目标时“仅建议，未评估”。

### L4 历史不同但没有会话关联

**卡片标题：** 两份可比请求的旧system时间字段不同。

**证据：** r20与r21相似历史中time值不同；只有appid和记录顺序，没有可靠session/parent。模板后差异可展示。

**判断：** 已观察字段差异，不能确认是同一会话改写历史。L4状态“需关联证据”；如果满足L1条件，可由L1提供独立字段调整建议。

**评估：** 不自动重构“旧历史＋新增消息”。显示“未评估：缺少可靠请求关联及追加位置规则”。不标死循环或编排失败。

**正常反例：** 后一请求完整保留旧消息，只增加assistant/tool结果，显示“正常增量追加”，不出历史改写问题卡。

### L5 结构化载荷格式不稳定

**卡片标题：** 相同JSON载荷以不同对象key顺序进入模型。

**证据：** 指定tool内容字符串分别为{"status":"ok","count":3}和{"count":3,"status":"ok"}；无重复key、字段值相同、数组次序未变，格式契约允许确定性生成，最终输入顺序确实不同。

**建议：** 仅该JSON字符串字段按固定key顺序生成；不改变消息数组或代码文本。

**评估：** 可生成稳定表示方案，经统一编码重放；展示P/C/R真实变化，不能保证格式调整一定改善缓存。

**零影响反例：** 外层请求JSON的key排列变了，但最终IDs完全相同。检查结果为“未检出缓存影响”，不生成低命中问题；如果做了格式副本评估，H/C/P变化为0，J变化另列。

## 3. Token内容页签

### T1 工具定义负担集中

**卡片标题：** 工具定义内容集中在3项长说明，可检查精简。

**证据：** 示例请求含20个工具，3项说明占工具定义展示表示字节数的主要部分。展示逐项大小、原文片段、模板参与状态；字段Token映射不足时注明“Token占比未知”，不画70%之类Token饼图。

**判断：** 优化机会，没有业务预算，不称“20个工具超限”，也不说未调用工具无用。

**建议：** 查看3项重复说明，提供具体替换文本后评估；按需加载仅作为架构建议。

**评估：** “未评估：尚未指定description精简文本”。不通过清空tools给出虚假节省。若用户提供明确文本替换，展示原/新description及保持不变的Schema，再运行同appid窗口评估。

### T2 工具返回超出已给定的内容约定

**卡片标题：** export_rows返回携带了约定之外的两列。

**示例前提：** 业务已给出的结果契约只允许id/status；当前载荷还携带raw_text/debug_info。这个约定是示例输入，不是平台默认策略。

**证据：** 具体tool消息路径、表格行数及四列，额外两列确实进入模型。

**建议：** 返回端按契约只保留id/status；保留tool调用ID、结果容器与行顺序。修改副本准确删除两个列字段，不截断全部结果。

**离线结果的构造展示：**

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 评估请求数 | 4 | 4 |
| P 输入Token | 32,768 | 24,576 |
| H 理想命中Token | 12,288 | 12,288 |
| C 理想重算Token | 20,480 | 12,288 |
| R 理想命中率 | 37.5% | 50% |

说明：4条均按相同规则修改，每条P从8192降到6144；假设首条H0，后三条各H4096。输入和理想重算各少8192 Token。ΔP是副本修改效果，不叫“两个字段精确占8192 Token”；未预测任务输出。

**无契约时：** 标题改为“大工具返回，待选择保留规则”，状态为优化机会，不自动裁剪。

### T3 文档在同一请求内出现两次

**卡片标题：** 同一48,000字节文档既在tool返回中，又被复制到下游工具参数。

**证据：** messages中两个准确路径、载荷摘要及一致性检查；是同一请求不同位置，不是两次请求各携带一次。重复出现字节为48,000，Token节省为空。

**建议：** 检查下游工具是否支持document_ref；支持且引用可解析时，用真实引用替换第二份正文。

**评估：** 当前协议只有document正文参数，显示“仅建议：无可用引用协议，未量化”。不会擅自将正文换成路径，也不会把48,000字节换算成预计节省Token。

**可评估分支：** 若既有协议已支持真实document_ref，保存具体引用和修改字段后，可对同appid窗口重放。结果标签为“引用替换后的静态输入变化”。

### T4 清理历史后输入减少，但理想重算增加

**卡片标题：** 历史工具结果可按已给定保留规则精简；缓存代价需一起看。

**示例前提：** 已有策略明确保留最近2个tool结果块，其余指定载荷替换为业务提供的可重读引用；不移除tool配对结构。未提供策略时只展示历史结果负担，不自动评估。

**证据：** 每个快照的结果块位置、哪些被策略选中、原/新内容摘要。无可靠session时不展示“第几轮”或持续增长趋势。

**离线结果的构造展示：**

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 评估请求数 | 4 | 4 |
| P 输入Token | 32,768 | 24,576 |
| H 理想命中Token | 23,040 | 12,288 |
| C 理想重算Token | 9,728 | 12,288 |
| R 理想命中率 | 70.31% | 50% |

说明：输入少8192 Token，但理想重算增加2560 Token，命中率下降20.31个百分点。样例按首条H0、后三条修改前H7680、修改后H4096构造。因为修改了旧前缀，不能只显示绿色的“输入减少25%”。

**业务结论：** 该方案减少输入内容，但本窗口缓存计算指标变差；展示取舍，不默认推荐上线。未评价重读调用、任务质量或真实费用。

## 4. 共用边界状态

| 场景 | 页面应该显示 |
| --- | --- |
| 无前序可比请求 | 低命中对照不足；Token内容仍按可读输入检查 |
| 字段未进入模板 | 原文内容事实可查，不归为模型输入负担/低命中原因 |
| 基线资产不一致 | 评估受阻，保留已核实字段事实；不填0收益 |
| 用户选较短窗口 | “本窗口重算基线”，前后均同窗口同空起点；原监控值另列 |
| 仅检查部分请求 | n/N，未查原因；不能称整个appid无异常 |
| 单项评估无改善 | 已完成，ΔP/ΔC真实为0；说明剩余差异，不隐藏 |
| 多项有重叠 | 同一字段/请求/方案关联，不能相加单项收益 |
| 组合尚未评估 | “组合未评估”，不给预计总收益或单项和上界 |
| 发现重复历史 | 只是内容证据，不能称Loop、失败重试或实际执行多次 |

## 5. 设计检查

九类卡片均须能回到具体规则、源证据和当前请求位置；没有操作规则则保留建议，没有完成评估则不显示收益。样例中的“可评估”是产品状态设计，不表示已有后端API。数值只检查H+C=P、R与差值算术，不作为真实缓存或Tokenizer测试。
