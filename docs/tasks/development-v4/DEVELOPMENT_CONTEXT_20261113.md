## 2. 开发agent的任务与分工

| 参与者 | 负责什么 | 协作边界 |
|---|---|---|
| 用户 | 确定需求/底线/优先级，批准前端展示和batch方案，操作真实页面验收，授权交付/现场执行 | agent不得替用户签字或把沉默当批准 |
| 产品/研究角色（用户安排时） | 提供原始需求、真实证据、产品方案、需求一致性评审 | 方案建议不等于源码事实；不接管开发/debug或持续调度 |
| V4代码开发agent | 独立核查方案/源码/测试，优化技术方案，负责获准公共层/后端/必要前端实现，逐批验证、问题闭环、最终E2E及缺陷修复 | 对实现负责，不把问题转给旧六线；不擅改产品范围/布局/门槛，不把打包当日常开发循环 |
| 镜像打包与审查角色 | 按具体授权独立交付复验、版本/Git、打包、容器一致性、现场prompt和交付记录 | V3曾明确授权其E2E与打包，不等于永久获得V4全部授权；产品代码缺陷交开发处理 |
| 华为现场执行方（获准时） | 真实数据/环境采证、复现、对应版本真实验证，返回可核对证据 | 本地合成不代替现场通过；不能自行部署或重算生产数据 |

开发应质疑过度设计、无源码支持的推论和不合理技术方案，先复用现有能力、提出最小必要改动。不要只复述研究结论，也不要把旧批次遗留自动扩成V4任务。旧V1/V2六开发线保持休眠，角色是否调整由用户安排。

## 3. 人机协作顺序与审批边界

1. **需求澄清/独立check**：明确要改变的用户行为、输入输出、验收底线与不做项；核对源码/测试/现场证据，列已支持、冲突、缺口和待业务确认项。能只读确认的先做，不把普通实现选择反复交给用户。
2. **涉及前端时先DEMO**：保持已批准四入口和L4/L5，给出具体差异、预期分析器效果、状态/指标/证据及列表详情交互。包括文案、数据展示接入、模块移除等，不因“兼容修改”而豁免。必须取得用户明确 **“前端展示审批通过”** 才能开发相应页面。既有V3批准只覆盖原稿；有新变化先展示新DEMO。
3. **面向agent的设计与batch计划**：前端稿获批后细化涉及它的实施计划；纯后端任务不人为增加DEMO。写出依赖、代码位置/函数、数据流/契约、最小改动、旧结果兼容、资源边界、失败行为和可执行验收。用户批准开发方案后才能写对应产品/测试实现、生成实际验证任务。方案不能停留在产品愿景，也不在需求未定时冻结预算/API/收益阈值。
4. **获准实施后持续推进**：按batch开发→验证→问题闭环→记忆更新→下一batch。门槛通过后自动继续，不每改一点就停下来问是否继续；普通授权范围内缺陷自主修复复验。遇到新范围/新页面设计/业务语义或门槛变化才提交明确差异审批。
5. **统一验证与用户人工验收**：批次通过后做真实全链、健壮性、历史兼容及对照设计的总check；用实际合成输入计算结果在本机前端展示，效果与已批准DEMO相似，数字不能来自DEMO。提供可访问URL、候选身份和操作步骤，由用户给出人工结论。
6. **交付交接**：交出确定候选、变更清单、测试/失败/闭环、限制、模型资产和启动身份。用户授权打包/Git/现场后由相应角色执行，不从V3授权推断V4已获许可。包体、容器、现场验收分别记录，不能互相替代。

沟通要求：主结论先说；报告已完成批次、证据、未通过/阻塞及下一步，不只列做了多少工作。耗时明显时说明具体瓶颈及解决动作，不能一小时没有可核查进度，也不能为赶进度省略必要验证。已知答案先从项目证据取得；确需用户决定时给具体差异与选项，不反复确认已批准步骤。

## 4. 每个batch的最小交付格式

batch以可验证的行为闭环划分，不能只按文件数量/前后端目录拆。依赖通常先公共契约与资源能力，再相关后端，再必要前端接入，最后统一E2E；按具体需求决定，**不是提前批准一组V4批次**。

每批必须包含以下内容，可以集中在一份增量执行记录的四节，不要求堆出四份空文档：

| 内容 | 必须回答 |
|---|---|
| 代码方案 | 目标/不做项、依赖、实际文件/函数、算法与数据流、兼容/资源/失败处理、验收门槛 |
| 问题记录 | ID、触发输入、候选/环境、预期/实际、根因证据、修复影响、当前状态 |
| 测试记录 | 命令与实际环境、独立输出目录、源码/输入/资产身份、PASS/FAIL/NOT_RUN、指标与日志、失败→修复→复验关系 |
| 闭环文档 | 门槛逐项结论、设计偏差、残余风险/待现场项、可宣称/不可宣称能力、下一批依赖 |

每批通过后立即增量更新本线入口/记忆，记录当前batch、候选、通过/失败、下一步和证据链接；共享文件先读最新，只按分工最小修改。与本批目标有关的问题未闭环不能宣布通过进入依赖批次。不通过删断言、删负收益方案、扩大预算或伪填结果换PASS。

最终状态至少区分：开发技术通过、用户本机通过、独立交付复验通过、包体/容器通过、现场验证；不以一个“完成”覆盖所有层次。

## 5. 继承的产品与计算约束

- V2四入口“用户监控、搜索与排行、异常分析、MA集群监控”及已认可L4/L5为展示基线。L1漏检优先修探测器，mem_limit优先修数据/内存处理，不能借修复增加独立功能页或通用任务框架。
- 小样本/full区别是**覆盖范围，不是计算完成程度**。大来源先按数量/原始字节/Token/单条与模型固定开销准入，再读取、解析、编码、比较；允许流式元数据/完整性检查。小范围可N/N，不能为“小样本”故意丢数据。
- 同一样本同成员/顺序/模型/初始缓存作before/after完整回放，复用统一编码和PrefixLedger计量；禁止粗填收益或按字符缩减直接当真实Token收益。P=H+C；百分点为100×(H_after/P_after−H_before/P_before)，P变化时不能只比较H。
- 不强制full、不自动升级全量、不设未经批准的任务/阶段硬时间截止；主动取消、真实内存/磁盘保护、工作量控制和清理等待与分析时间上限分开。V3的300条/64MiB/400万Token是该版本工程上限，不是必须取300条或V4恒定默认；根据实测模型开销可能更小。
- 新样本结果不套旧full/>1pp展示过滤。完整正/零/负、无适用对象、无实际修改、未评估、取消/资源不足分别表达；未完成不填0。单方案收益不可相加，各方案修改数之和不等于去重覆盖数。
- clock固定化指受支持标签内部替换为NORMALIZED，保留标签与外部内容；局部高亮不等于完整修改范围，不能宣传只改秒数或业务无损。模型/上下文/工具协议/业务时间语义均需保护。
- 浏览只读取已发布成果，不在GET/页面访问时触发分析。报告、样本、任务、模型、来源和service instance身份须一致，历史结果保持原口径；损坏拒读，不能悄悄退回旧checkpoint伪装完整。
- Token新规则/显式full/模板分组/组合评估等V3未实施或延期内容不会因命名V4自动获准。新模型/新规则也不能冒用旧模型或旧报告身份。

## 6. 本地、现场与证据保护

**本机无真实数据时**：先要求授权现场方提供五类信息——输入结构与量级、脱敏关键片段、模型/模板身份、现象与实际结果、正文中的关键源码/日志证据。本地合成保留长度、tools数量/协议、历史关系、字段位置和差异结构，控制样本数；不用真实个人身份做展示标签，不把recipe/期望收益写进输入。真实数据不足不意味着可以只有mock，也不要求为每个疑问重跑全量。

**验证层次**：单元/集成验证边界和失败；实际CSV→监控→样本→发现→plan→实算→报告→浏览器验证主链；模型固定资产验证计量；容器验证包体；现场真实结果验证实际业务。mock用于展示状态与错误分支，必须标明，不能代替真实编码/浏览器链。

**资源验证**：同模型/请求分布下放大父来源，记录父N、选样N/字节/Token、校准、实际读取/编码/比较、RSS和退出原因；不能仅看最终N或健康200。固定资源对照允许因实际模型开销不同而自动调整N，需重算校准公式与逐样本计数，不能要求不合理的样本数恒定。进程RLIMIT_AS通过不等于整机cgroup/所有低内存环境保证。

**每次新候选E2E**：核对并正常停止旧TokenScope服务/worker/容器，确认退出/端口释放，用确定源码、新dist、新空state、新浏览器冷启动；不能另换端口保留旧版并行。保留旧state/输入/包/证据，不误停无关项目。同版本恢复与历史兼容在独立记录/一致副本上验，不改原件。

**每次写测试产物前**：核实解析后的绝对输出路径在项目内，使用唯一attempt目录、排他创建，禁止覆盖历史JSON/XML/日志/截图。测试失败保留，修复另写复验；先定位选择器/测试条件/环境问题与产品问题，纠正验证方法需解释批准门槛、保留原FAIL和独立核验证据，不能降低业务门槛。

**人工验收服务**：实际浏览器检查报告而非只测SPA200，核对本机/WSL/远端localhost，记录PID/命令/state/版本/端口与健康检查。提供服务时核实当前可访问，旧PID和“昨天可用”不是健康证据；进程退出如实恢复，不臆断原因。

**现场操作**：以最新单次授权决定复用还是新state重算。V3早期“不重算约15万条”后来获用户允许新state全量监控重算，不能将其中任何一次决定当永久规则。始终保护旧数据/包、核对设备与资产、保持获批端口/隧道和人工确认要求；回传单Markdown关键证据嵌正文。需要新现场执行/发消息时必须有授权，不自动SSH、派单或代签业务安全。
