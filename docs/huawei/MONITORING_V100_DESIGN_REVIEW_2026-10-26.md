## 不直接沿用的报告推断

- `nproc --all=224` 和 `/proc/self/status` 的宽 CPU 列表与 online/affinity=40 不一致；采用交叉一致的 40 个可调度逻辑 CPU。报告对旧 coreutils/内核行为的原因解释没有另行源码验证，不作为设计事实。
- 报告建议“8–16 并行，再按 min(文件数,16)”混合了文件并发和单文件内部并行。监控目标是每文件两小时；本版明确 `max_active_runs=1`，一个文件内部共享 8 个计算槽位，调优至 16 须有性能和宿主干扰记录。不能只因有三个文件就把编码并行预算定为 3。
- cgroup 内存哨兵值在原文写成精确 `2^63−1`，实际输出为 `9223372036854771712`。设计仅将其视为本次可见链上没有实际约束的报告，不使用该数做可分配内存预算；未来容器限额重新检测。
- GPU proc 证据足以确认两张 V100；不能从缺少 `npu-smi` 进一步证明机器绝无其他硬件。首版不需要这个推断。驱动故障已支持“nvidia-smi 不可用”；CUDA 计算和 GPU 容器没有直接运行测试，均保持未验证。
- glibc 2.42 只是命令输出，来源和真实二进制兼容性未核实；镜像固定用户态也不替换宿主内核。不能用 Docker 版本或 Python 版本一致推出镜像一定能运行。
- 低负载、大内存和空闲磁盘是快照；没有长输入/词表/真实 CSV 数据支撑“无内存瓶颈”“离线包存放无忧”或两小时达标。启动时必须重新检查预算与剩余空间。

以上核对不改写原报告，也不要求现在追加远程调查。旧内核兼容性、资源峰值和代表数据耗时纳入 B006 现场验收；若失败，在本机修正相关代码或镜像后重测，不能要求现场 Agent 临时升级宿主环境来掩盖兼容性问题。
