# 低命中率与 Token 异常分析产品方案讨论稿

版本：v0.2。日期：2026-10-30。用户已明确首期聚焦低命中率、Token内容分析并纳入离线修改评估；流程和字段仍为讨论稿，暂不编码。详细入口：[首期流程](PHASE1_PLAN.md)、[结果与证据字段](RESULT_FIELDS_DRAFT.md)、[展示样例](DISPLAY_EXAMPLES.md)。

面向业务 agent 的开发者和编排维护者，帮助回答：哪些输入变化影响了复用、哪些内容或步骤增加了消耗、证据在哪里、可以怎样调整、如何验证调整有效。网关和 MaaS 同事参与定位转换、编码及数据边界。

以现有监控运行中的 **appid × 模型服务 × 数据范围** 为报告入口提案，提供低命中率与 Token 异常两个视图。首期细化请求内容、前缀证据和离线修改评估；取得可靠调用关联后，再增加跨请求重试、上下文增长和无进展循环分析，补充数据清单见首期流程。一个问题可同时影响两类指标，报告应相互引用，避免重复计算收益。

依据：[首轮调研](../../research/topics/AGENT_ANOMALY_RESEARCH_2026-10-30.md)、[监控已实现接口](../../contracts/MONITORING_IMPLEMENTED_API.md)、[统一计量](../../contracts/MONITORING_V1.md)、[V1现场验收](../../huawei/MONITORING_V1_ACCEPTANCE_20261030.md)、[UI-01](../viewer/PROTOTYPE_V2_UI_01.md)。本稿只收敛产品对象、场景、输入和展示；具体算法、API、存储、开发批次由后续详细设计承接。

## 1. 分析对象与用户问题

| 层级 | 对象 | 用户应能获得的答案 |
| --- | --- | --- |
| 报告范围 | 一个已完成监控运行中的appid与明确绑定的模型服务 | 本次看了哪些数据，主要问题是什么，哪些方向尚不能判断 |
| 问题 | 在这个范围内有共同证据的一类现象 | 变化/消耗发生在何处，已证实什么，哪些原因还待核实 |
| 请求证据 | 一条请求，或有明确比较依据的请求对/请求集合 | 输入、来源字段、模板后前缀、J/P/H/C/O，以及差异位置 |
| 过程证据 | 已可靠关联的session、turn、工具或子任务序列 | 重试和重复是否发生，是否有进展，是否达到停止条件 |
| 修改评估 | 某项具体调整作用于明确样本和固定配置 | 修改前后有什么变化，收益适用哪一组数据，业务效果是否验证 |

appid是租户/应用范围，不能直接当作一个agent或session。模型服务与编码模型分别保留；V1没有服务绑定时显示原运行模型身份，服务来源未确认则不猜common_name。监控V2的接入依据各线实际实现/验收，不把设计中的接口当作已验收能力。

本稿的主要入口是用户侧请求数据。MA侧的规格×UUID、跨appid共享和pre/now预热有不同语义；MA对照可以作为后续关联背景，不能与用户侧结果直接相减得到“缓存损失”，也不在此增加真实引擎TTL、淘汰或路由归因。

## 2. 现有数据与可支持的判断

### 2.1 当前已经有的基础

| 输入或能力 | 已核对的事实 | 对方案的用途与边界 |
| --- | --- | --- |
| CSV与原始请求 | 五列为hash_id、appid、model_handle_start_time、completion_tokens、request_input；正文可含messages、tools及历史tool_calls/tool消息 | 可分析请求内容及可见历史；不保证含稳定session/turn或完整执行记录 |
| 请求身份 | 唯一定位为run_id与source_record_index；hash_id可重复且保留每行 | 问题引用回到原记录；重复hash_id不直接判为重试，也不自动去重 |
| 监控指标 | 请求级J/P/H/C/O、J/P/C分布及排名、聚合命中率、配置及质量身份 | 选取长输入、高重算等候选，保留相同口径；O只有源输出计数，不含本次完整响应正文 |
| 原文与轻量证据 | 正文/证据只读接口；source_fields包含字符串JSON Pointer、字符数、UTF-8字节数和摘要 | 能定位大字段、对比字段变化；不代表字段参与了模板，也不是精确Token贡献 |
| 模板后Token | 后台保存输入IDs及摘要；普通GET未直接提供完整模板后文本或全部IDs | 可作为后续分析内部复用基础，公开接口是否扩展另行设计 |
| 显式编码复核 | explain复用统一编码，核对IDs摘要并返回模板后offset；原JSON来源归属仍为unknown | 可定位模板后差异，不能据此保证每个Token都映射到原字段；不放到页面GET里执行 |
| 缓存事件 | 已存匹配块数、发布块数等逻辑摘要；事件不包含真实阶段耗时 | 可解释模拟规则；未保存每个命中前缀的来源请求，不能直接展示“命中来自某请求” |
| 触发信号 | 监控可发布阈值信号，当前无消费者时为pending_consumer | 可以作为候选入口；已有信号不代表诊断已执行 |

源码核对入口：[原始读取](../../../src/tokenscope/ingestion/csv_reader.py)、[字段引用](../../../src/tokenscope/encoding/models.py)、[编码与复核](../../../src/tokenscope/encoding/batch.py)、[保存](../../../src/tokenscope/encoding/stage.py)、[只读证据](../../../src/tokenscope/monitoring/views.py)、[缓存规则与事件](../../../src/tokenscope/monitoring/simulation.py)。这里只读核对，未运行现场数据验证。

### 2.2 当前输入必须保留的边界

J是原JSON文本的Token数，P是模板后输入长度，H是理想可复用量，C=P−H，O是源输出计数。P−J不能称作纯模板开销。字段字节占比不能改名为Token占比；独立编码各字段后求和，也不能当作精确的P分解。

请求正文中的工具历史是一次输入快照，同一条历史事件可能在后续多条请求里反复出现。它可支持“该请求携带这样的记录”，不能未经去重和关联就累加为实际工具调用次数。model_handle_start_time只用于现有排序和范围展示，不代替工具开始/结束、用户到达或真实执行时长。

当前理想缓存为空起点、无限容量、完整输入块发布，并受MTP、CP和所选链式规则约束。分析应先区分前缀变化、首次出现/新增内容、窗口前历史缺失及规则限制；不把低命中直接标为编排错误。Qwen/DeepSeek保留链式近似说明。

### 2.3 补充输入按问题申请

| 要回答的问题 | 最少补充的信息 | 缺少时怎样呈现 |
| --- | --- | --- |
| 是否为同一agent的连续请求 | 稳定session/run/agent标识、请求引用及顺序；分支需parent或依赖 | 可做结构相似请求对比，不称相邻turn、历史被改写或会话增长 |
| 一次工具调用是否失败后重试 | 唯一工具事件/调用ID、名称、参数、结果或摘要、状态；retry/attempt或可验证关联 | 只展示输入历史中的重复/错误线索，不给真实重试次数 |
| 是否有无进展循环 | 上述调用关联、任务目标/完成状态、状态变化、终止原因与预算；必要时人工业务确认 | 显示疑似重复及待核实点，不输出已确认死循环 |
| 子agent是否重复工作 | 父子任务、角色、handoff、分支和结果关系 | 不从请求量或多个agent名称推断冗余 |
| 输出是否过度冗长、思考是否异常 | 本次响应内容与明确的usage/思考口径、任务要求 | 只报告O计数偏高，不判断输出内容浪费 |
| 输入变化是否来自网关 | 转换前后关联、网关/编排版本、所用模板与配置；必要时输入字段来源 | 只能确定收到的输入变化，责任来源待核实 |

以上是数据需求，不预设采用OTel或特定trace格式，也不增加监控CSV必填列。字段可来自正文、已有日志或补充关联材料，但应标明来源和可靠性。现场先用少量连续脱敏样例确认覆盖，再讨论接入形式；生产正文留现场。

## 3. 低命中率分析

### 3.1 核心输出

每个发现尽量回答四点：**哪些输入有可比关系、最早在哪里变化、变化影响了哪些后续复用、可以怎样稳定它**。如果没有合适历史或配置不支持比较，就说明原因，不强行生成优化项。

分析入口可以是已有低命中信号，也可以由用户主动选取已完成范围。低于某百分比只用于筛选；首期不设通用“低于80%即异常”目标。跨窗口比较需先确认服务、编码、缓存规则、有效集合和预热条件可比；当前单窗口即使没有历史基线，也可以做内部请求对照。

### 3.2 典型场景

| 场景 | 需要的输入 | 证据与结论边界 | 建议展示 |
| --- | --- | --- | --- |
| cch、时间戳、请求编号等动态内容进入前部 | 两条以上可比正文、固定编码、输入IDs；必要时复核模板后位置 | 标出变化值和最早分歧；必须确认字段进入模型输入。只在JSON中出现、模板未消费时，不能归因为前缀损失 | 评估移到输入后部或保留在模型外元数据；先确认业务、审计和鉴权依赖 |
| 工具顺序或定义变化 | tools原始顺序、定义差异及模板后证据 | 区分同集合顺序变化与合法工具版本/权限变化；说明最早变化项 | 对稳定版本评估确定性排列/序列化；实际工具变化则评估分组和版本管理 |
| 历史内容被重写 | 可靠连续关联、相同历史项跨请求对应 | 对齐原历史后展示改写位置；没有关联时只称内容差异 | 检查动态包装、历史序列化和摘要更新，保持不需要改变的历史稳定 |
| 动态检索/环境内容排在稳定说明之前 | 原文、结构及模板后的顺序 | 展示前部动态内容与后续稳定片段；后缀相似本身不等于可直接命中 | 在任务语义允许时评估位置调整、稳定说明复用 |
| 压缩、截断、模型/模板选项变化 | 连续关联，压缩/配置事件及输入差异 | 标为上下文/配置变化；可能是合理管理，不默认是故障 | 解释复用代价，评估触发时机与保留策略，联合任务效果验证 |
| 首次出现、合法新增或窗口/规则限制 | 已有时间、历史范围、P/H/C、块长/MTP/CP和cache状态 | 列为解释项；无历史不冒充动态字段原因，显式关闭缓存也不报编排缺陷 | 需要时补充分段/预热背景，说明剩余不可归因范围 |

### 3.3 请求对照如何解释

优先比较同一可靠session中的连续请求；没有session时，在同appid、同服务、同配置范围内寻找工具/说明等结构可比样例，并明确标注“结构对照，非已确认同一会话”。不为不同业务内容制造应该一致的假设。

用于解释历史缓存可用性的对照必须先于当前请求，排序沿用监控规则；后续请求只可说明模式重复。对照请求是展示样例，不宣称它是实际缓存唯一来源：现有账本可由多个更早请求形成，且未保存来源归属。若只查了部分候选，显示候选范围，不称全量最优对照。

差异页同时展示原字段变化和模板后差异。JSON Pointer存在但来源映射未知时，只显示字段与相关片段，隐藏精确Token坐标。Token分歧、块对齐/MTP边界分别解释，不能把首个不同字符的位置直接当作H。

“差异后的稳定内容”先作为受影响线索。只有完成固定条件的修改评估，才展示可减少多少C或命中率可变化多少；不会把整个后缀都默认计入可挽回收益。

## 4. Token 异常分析

### 4.1 请求内容与调用过程并列

请求内容分析回答“这一条输入携带了什么、哪里大或重复”；过程分析回答“一个任务为什么反复调用、上下文为何增长”。两者共同解释累计消耗，但只有可靠任务关联时才能给出每任务调用数、累计Token和过程结论。

Token异常分析不以低命中率为前置条件，高命中也可能伴随无效循环。高P、高O或高调用数都是候选现象。正常长任务、合理轮询和必要重试可以消耗较多；最终卡片标题应描述观察事实，不直接宣称“工具返回无用”“已经死循环”。

### 4.2 典型场景

| 场景 | 当前可获得的线索 | 需要补齐或核实的证据 | 建议展示 |
| --- | --- | --- | --- |
| 大体积工具定义、system或工具返回 | P/J排名、字段字节、角色、消息数量、片段 | 精确P组成需可靠映射；内容是否必要需任务要求 | 展示最大来源字段；评估返回条数、摘要、分页、按引用取正文或工具分组 |
| 重复内容或多层序列化 | 同一请求中的重复文本/结构、转义字符串、字段位置 | 模板是否消费、重复是否属于业务引用或必要历史 | 展示重复的两处及重复范围，评估减少重复注入/包装 |
| 输出计数偏高 | O及同范围请求对照 | 响应和usage口径、任务完成要求 | 给出计数线索；取得正文后再判断冗长、思考或输出约束 |
| 上下文持续增长 | 可靠关联后逐请求P/H/C/O与消息/字段变化 | session顺序、压缩和分支信息 | 展示增长曲线及新增来源，评估保留窗口、压缩、外部引用 |
| 工具失败后参数未变的重复尝试 | 输入快照可含工具调用和错误文本 | 真实事件身份、错误状态、attempt及调用关联 | 历史线索与执行时间线分开展示；建议区分参数错误和可重试故障 |
| 相同操作持续无进展 | 关联调用的工具、参数/结果和状态变化 | 任务目标、正常重试/轮询规则、终止原因、完成标准 | 先标疑似无进展，展示连续证据；建议进展检查、预算和停止策略 |
| 子任务重复或取消后仍执行 | 关联的分支、工具/模型活动 | 父子任务、共享状态、取消/完成事件 | 展示依赖和重复范围，建议职责、结果共享和取消传播调整 |

### 4.3 组成与过程的展示口径

默认展示可核对的P总量和来源字段大小。若只有字符串字节计数，图表明确叫“原文字段大小”，不画加总为P的Token组成饼图；容器与子字段不重复累计。取得完整、无重叠的模板后归属后才使用可加总的Token堆叠图，并保留“模板/未归属”部分。部分映射保留partial，不用精确百分比填满未知区。

过程图按实际可得数据展示模型调用、工具事件、错误、重试和终止。只有输入历史时改为“请求内历史片段”，不补造执行时间。跨请求共享历史去重依据不可靠时，不显示真实工具调用总数。累计输入Token表示每次请求携带量之和，不代表唯一文本量；P、C、O分别展示，不合称计费Token。

## 5. 报告入口与阅读流程

建议首期以用户显式发起分析为主，既可从监控信号跳入，也可直接选择已完成数据。自动消费信号的策略另行讨论，避免把目前pending_consumer解释成自动分析已经工作。

```mermaid
flowchart LR
    A[监控范围或问题信号] --> B[确认运行与分析范围]
    B --> C[显式发起分析]
    C --> D[后台形成并保存报告]
    D --> E[范围摘要与两类发现]
    E --> F[查看证据与修改建议]
    F --> G[查看已有评估或显式申请评估]
```

发起时固定原监控运行、appid、服务/模型身份、配置、筛选范围、已有信号和补充关联材料。已有报告可直接打开；用户另行发起分析/评估才产生新工作。打开页面、切换tab、排序、查看证据只读取已保存结果。

初次分析建议覆盖所选appid的完整有效范围，以高P/C、低复用或大字段请求优先深查。大范围采用抽样/预算时，报告分别给出“选定范围”“已检查范围”“深度复核范围”，不把样本结论外推成全量。筛选时间片时，单请求H/C仍属于原监控运行的完整回放历史；若要求从切片冷起点重算，须作为另一个明确评估。

### 5.1 范围摘要

页面顶部显示appid、模型服务/编码模型、源运行和数据时间范围、报告生成时间。并列展示有效请求数、J/P/H/C/O和理想命中率，以及本次已检查数、可比较数/可关联数。质量详情保留文件读入/跳过数量和原因；不能归属appid的跳过行只放文件级，不能摊成租户跳过数。

两类tab分别列出问题和分析覆盖情况。没有可靠session时，“调用过程分析”显示“缺少可靠调用关联”，请求内容发现仍可查看。没有发现、没有分析和输入不足是不同状态：

| 状态 | 用户应看到的内容 |
| --- | --- |
| 尚未分析 | 当前范围无报告，提供显式发起入口 |
| 分析中 | 已提交范围与状态，保留可查看的上一版报告及其时间 |
| 有发现 | 问题列表、证据、建议和可得评估 |
| 已检查但未检出 | 已检查的场景与覆盖；不写“没有异常” |
| 部分可分析 | 已完成部分、缺失输入、受影响结论及已有发现 |
| 无有效输入或分析失败 | 具体原因与可采取的动作；不把失败展示为空建议 |

### 5.2 问题卡片

沿用UI-01的业务建议卡片和详情层级。卡片显示：观察事实标题、类别、业务位置、结论状态、已确认涉及的请求数及分母、具体建议摘要、收益状态和进入详情的入口。

默认按已证实涉及请求数排序，同值按证据充分程度；只有同单位、同范围的收益才可切换排序。请求级与任务级卡片分别标注单位，不把“每请求节省”与“每序列节省”混排。覆盖不足的项保留显眼说明，未量化项不显示0。

UI-01已有百分比置信度和示例收益。建议本阶段用可解释的结论状态替代未校准的置信度百分比；保留“证据—建议—评估”布局。原型不在本轮修改，后续由异常分析前端依据确认后的方案调整。

### 5.3 证据详情

详情先给业务解释，再展开技术证据。建议顺序为：

1. **发生了什么**：事实、涉及范围及本次可确认的程度。
2. **证据在哪里**：请求引用、业务字段、片段或时间线，必要时两列对照；显示比较关系及缺失信息。
3. **建议怎样改**：修改对象、原因、示意、保留条件和验证方法。
4. **评估结果**：基线、具体变更、单位、样本和配置、前后结果；没有评估时直接说明。

业务位置如“工具定义→第4个工具→描述”，技术展开保留原JSON Pointer、源记录和摘要。原文、模板后文本、工具事件是不同证据类型。坐标带单位与起始约定；未可靠映射时不画精确字段Token高亮。脱敏内容注明展示替换不参与原指标计算，原始证据保持不变。

## 6. 结论状态与覆盖范围

原因判断与收益评估独立表达，避免用一个“置信度”同时代表事实可靠性、原因正确性和优化成功概率。

| 结论状态 | 适用示例 | 允许的表达 |
| --- | --- | --- |
| 事实已核实 | 已比对的工具顺序不同、某输入字段变化、重复内容可定位 | 陈述发生了什么以及涉及哪些已检查记录 |
| 原因待核实 | JSON动态值与低H同时出现，但未确认进入模板或责任来源 | 提出候选原因和下一项核查，不断言因果 |
| 输入不足 | 没有会话关联却要判断跨turn循环 | 明确缺少什么及影响哪项判断，仍展示可获得的事实 |

一张卡片可以同时写“已核实工具顺序差异；对复用的影响待评估；调整顺序的业务效果待验证”。已核实输入差异并不等于已核实其导致全部命中下降。

至少分别统计：选定有效请求数、已检查数、适用比较/关联数、已核实涉及数、已评估数。每个比例注明分母；“评估覆盖率”使用已核实涉及范围中已完成同项评估的比例，若仅抽样则直接写“已评估n条样本”，不混作任务完成进度。抽样命中模式不能自动扩为全量受影响数。

同一请求可能出现在多条发现中，受影响数量和单项收益均不相加。全范围尚有未归因部分时显示其范围；不把未归因自动当作应唤醒自进化Agent的信号，后续启动依赖保持不变。

## 7. 建议与收益如何形成可验证行动

### 7.1 每项建议的内容

建议写清修改位置、具体动作、成立条件和验证方式。例如cch场景应说明“检查网关是否把动态标记注入模型输入；确认功能依赖后，评估移出稳定前缀或保留为模型外元数据”，不能仅按字段名自动删除。工具顺序建议先限定同版本/权限集合；大工具返回建议给出分页、摘要、引用等可恢复的读取方式；重试建议区分参数错误与临时故障，并明确停止/退避条件。

报告展示修改前后示意并支持复制建议文字；自动修改业务编排、网关或现场数据不包含在本稿范围内。涉及任务内容裁剪、工具变更或停止策略时，验证至少同时看业务正确性/完成情况与消耗。

### 7.2 收益分层

| 状态 | 展示内容 | 解释边界 |
| --- | --- | --- |
| 未评估 | 定性建议及需要的验证 | 不填预计百分比或虚构节省量 |
| 离线输入评估 | 同一输入样本和固定配置下的J/P/H/C前后对照 | 说明模拟收益；不承诺实际命中、费用或时延 |
| 业务验证 | 代表性任务的完成/正确性、重试、停止和消耗对照 | 涉及新执行结果，不从静态裁剪自动推断 |
| 现场对照 | 有明确请求集合和生产观测的真实命中、消耗或时延结果 | 保留流量、初态和部署差异，按实际可比程度解释 |

低命中离线评估沿用同一监控编码和缓存规则，对明确变更后的完整评估序列按原顺序回放，保留历史/冷起点及其他条件。仅改变目标字段；需要修改历史中的重复引用时，说明一致变更规则。缩小样本而丢弃前序缓存时，重新给出同条件基线，不与原全窗口结果直接比较。

展示 `R前=ΣH前/ΣP前`、`R后=ΣH后/ΣP后`，命中率差为百分点；重算输入变化为`ΣC前−ΣC后`。修改可改变P，不能固定旧分母计算新命中率。结果可以无改善或变差，原样报告。

Token内容评估分别展示ΔJ、ΔP及必要时的ΔC，不把源字段字节差当Token节省。静态输入修改无法确定未来输出O、工具决策和调用次数变化；过程类建议在未获得受控执行对照前不给“可省多少次调用”的数值承诺。全任务/全窗口/每条请求的单位始终分开。

单项评估与组合评估分开；没有组合回放就不累加收益。模拟Token变化也不直接换算费用、TTFT或GPU利用率，相关结论需要对应价格/usage或性能观测及适用条件。

## 8. 三个展示示例

以下仅说明信息结构，不含真实诊断或已执行评估数值。

### 8.1 动态标记影响前缀

卡片标题为“稳定说明前的动态标记跨请求变化”。详情并列展示两个可比请求中的`cch=…`差异，标明它位于哪个消息/字段、是否已在模板后定位，以及最早分歧处。结论写“标记变化已核实；复用影响待评估”，而不是“cch必然是全部低命中原因”。建议检查注入来源和功能依赖；收益栏显示“未评估”。

### 8.2 工具返回占据较大原文字段

卡片标题为“检索工具返回包含大段正文和调试字段”。详情显示对应tool消息、字段字节大小和请求P总量。若尚无精确Token映射，不展示“该字段占72K Token”；是否可只返回摘要由业务确认。建议先返回摘要与引用、按需取全文，评估栏保留输入节省与任务效果两项。

### 8.3 错误后出现相同参数

只有一条请求历史时，标题为“输入历史中出现相同参数与重复错误”，标明历史中可见的次数，不声称真实工具执行次数。取得唯一调用事件和重试关联后，才展示真实过程时间线；再结合状态和任务目标判断是否无进展。建议返回可修复的参数错误，并为不可恢复错误设置停止/转人工条件。缺少执行对照时不量化可节省调用。

## 9. 建议的首期边界与协作依赖

| 范围 | 当前数据下的产品建议 | 依赖 |
| --- | --- | --- |
| 首期基础 | 已有范围/质量摘要、问题卡片与证据；原文字段大小、重复内容线索；可比请求的动态字段/工具差异及条件化建议 | 后续实现诊断逻辑与持久报告，复用现有请求/计量能力；“可行”不表示现已实现 |
| 首期已纳入 | 模板后前缀核对、单项离线修改评估及可得的来源定位；详见首期流程 | 复用监控公共能力，保留完整回放历史；可靠映射不足时降级，基线不一致时阻断对应评估 |
| 有条件的过程分析 | 可靠关联后的增长、失败重试、无进展与子任务问题 | 先确认实际关联覆盖与执行证据，再收敛场景和判定规则；不因缺失而从长期产品范围删掉loop |
| 独立后续讨论 | 实际缓存运行归因、自动消费、计费/性能预测、自进化调查 | 相应生产观测、授权与专属设计；不阻塞请求层方案 |

监控唯一维护Tokenizer/Template、计量和缓存模拟；本线提出需要的IDs/配置/事件读取、选择性复核和定位缺口，后续登记公共修改的唯一维护者与接入版本。字段精确归属属于尚待共同确认的能力，不能以已有source_fields替代。

异常分析后端负责形成发现、证据、建议和评估结果；异常分析前端消费保存结果并沿用UI-01风格。母会话先与用户收敛产品方案，之后按用户启动两条详细设计/开发线；本稿不定义新API路径、不修改S0、不生成HTML或启动开发batch。

首期方向与纳入离线修改评估已由用户明确，不再作为待选项。后续收敛候选/深查预算、修改规则和字段细节，核对[PrefixLens现场证据](../../../prompts/sessions/HUAWEI_PREFIXLENS_SERIAL_DETECTOR_RESEARCH.md)；过程分析按补充数据清单保留。接口冻结和两条开发线仍按用户后续启动。
