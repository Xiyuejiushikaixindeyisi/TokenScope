# TokenScope V2 用户监控后端设计

版本：v0.1，**审批稿**；2026-10-30。负责人：用户监控后端 session。本稿提出设计供用户审批，不代表代码、接口、现场配置或交付已变更。V1 已验收发布身份不变。参考[V1设计](../DESIGN.md)、[实际接口](../../../contracts/MONITORING_IMPLEMENTED_API.md)、[现场验收](../../../huawei/MONITORING_V1_ACCEPTANCE_20261030.md)和[MaaS架构](../../../architecture/MAAS_REFERENCE.md)。

## 1. 范围与已确认口径

本线覆盖 V1 时间格式、模型别名、DeepSeek思考模式及内网访问问题；用户侧搜索排行；指定 P90 TTFT 的最低理想命中率参考估算。数据以 GB 用户视角按 **appid × common_name** 独立统计；当前每 CSV 空缓存、无限容量、上一请求可缓存输入立即可用，普通链式近似沿用 V1。输出为服务级潜力，不代表生产实例真实命中。MA监控、异常分析、前端实现和 hybrid 仿真不在本稿范围。

| 已确认事项 | 本设计处理 |
| --- | --- |
| CSV时间为UTC | 无时区时间按UTC；携带时区的时间转UTC；展示时区沿用V1 |
| DeepSeek生产缺省未知，以现场报告为准 | 新配置默认采用现场 thinking_disabled，明确标注现场假设，请求显式选项优先；不宣称生产缺省已核实 |
| 首版TTFT估算 | 目标减设定等待时间，按性能校准反推可计算Token，结合模板后P90输入长度；不建等待队列、不逐条展示 |
| 排行重算Token | 单请求 C = 模板后输入 P − 理想命中 H；使用 C 众数区间内 C 的算术均值 |
| 原JSON长度 | 对原JSON文本进行tokenization后统计，不能用字符数；与模板后输入和重算量区分 |

## 2. V1兼容与访问

### 2.1 时间

在现有解析路径增加严格 `DD/MM/YYYY HH:MM:SS` 及可选小数秒，保留原支持的ISO格式和精度；非法日期、混用不支持的格式照旧记录原因，不猜测月日。输入无时区标记按用户确认的UTC解释，有明确offset转为UTC；不改写原CSV，旧结果不重算。验证跨日、闰日、小数秒、非法日期和原有ISO兼容。

### 2.2 模型别名

复用已有模型设置的显式 aliases 和 revision 快照，提供现场报告中对应模型变体的明确映射作为新安装的初始候选；不得用前缀/模糊匹配。已存在的设置不能被升级静默覆盖，名称冲突需明确报错并要求配置修正。历史运行继续保留原快照。报告中的变体及模型映射以[现场验收及原报告](../../../huawei/MONITORING_V1_ACCEPTANCE_20261030.md)核对，模型和编码资产身份仍须一致。

### 2.3 DeepSeek 模式

对新建配置的 DeepSeek 默认 profile 提议为 `thinking_disabled`，按用户决定采用现场模式；显式请求选项优先，结果与配置显示该选择及“现场假设、生产缺省未知”。已有设置、已完成结果不静默改写，旧 `default` 未决的既有配置须明确迁移或由用户选择；不能把 `default` 自动解释为已核实的生产值。配置变更仅对新运行生效；兼容现有明确开启/关闭选项。

### 2.4 内网访问

当前 `deploy/monitoring/compose.yaml` 发布为 `127.0.0.1:18000`；建议提供可配置宿主绑定地址，内网部署可选 `0.0.0.0:18000` 或指定内网网卡，容器内部健康检查仍用容器loopback。访问地址为服务器内网IP/域名加端口，`0.0.0.0` 是监听地址而非浏览器访问地址；`0.0.0.1` 不承担此用途。检查端口占用、网络策略及可达范围；发布到所有网卡可能扩大访问范围，应按现场允许访问的网络选择绑定。此处是待审批方案，不改V1运行配置、不实施部署。

## 3. 统计与搜索排行

有效请求定义沿用 V1，同一CSV重复hash_id仍作为独立记录；读入/有效/跳过及原因必须可见，缺失不能当零。每个文件与模型服务绑定；若当前数据未提供 common_name，以用户明确绑定的模型服务作为分组身份，禁止从文件名静默猜测。多CSV或跨运行聚合、数据库采集不在首版默认范围，同一查询固定一个已完成运行。

对每个 appid×common_name，以 P 为模板后输入、H 为理想命中、C=P−H、J为原JSON编码Token：

| 指标 | 定义 |
| --- | --- |
| 请求数 | 有效请求行数 |
| 重算Token总量 | ΣC |
| 理想命中率 | ΣH/ΣP；ΣP=0为无值 |
| 代表性重算长度 | 请求数最多的 C 长度区间内，ΣC/该区间请求数，单位Token/请求 |

提议沿用 V1 默认 5,000 Token 左闭右开分箱及 1K/2K 可选宽度。针对排行增加单独的**等宽开放范围分箱**，不把 V1 `≥200K` 汇总桶当成等宽众数箱：C≥200K 按同样宽度继续分箱，确保长尾不能因汇总而伪造众数。并列众数全部保留，各自返回区间、数量、占比及均值；排行默认按并列众数中**最低区间的均值**排序并标注并列，避免选择不确定。该排序规则及分箱方式为审批提案。空集返回无值，不以0冒充；区间均值使用原始整数求和除以计数，展示可四舍五入，排序使用未舍入值。

按appid关键词搜索和四项指标的范围筛选、升降序排序与分页；默认请求数降序、appid稳定排序。缺值始终排在末尾；不同模型服务/不同运行不混合排名。统一从已完成分析结果读取，页面访问不触发重编码或仿真。V1既有快照/接口保持原样；新能力采用版本化扩展或新读取接口，字段命名与S0兼容性在实现前单独固定，不把本稿视为已发布契约。历史数据如果缺少等宽分箱均值，可由已保存的请求facts后台生成索引；生成前明确显示未就绪，不在GET中触发计算，不改变原seal。是否可利用事实数据、磁盘和回填代价在开发前核实。

## 4. P90 TTFT目标的参考估算

### 4.1 输入与计时边界

选定一个已完成的 appid×common_name 结果，使用有效请求模板后输入长度 P 的 nearest-rank P90（V1口径）；用户提供目标 T 和等待情景 W，均转换为秒。性能校准必须绑定模型、部署、负载/批次、缓存读取条件和TTFT测量边界，时间戳及分位数口径需可追溯。MaaS描述的model_ttft从GF发出请求开始，不包含GB排队；结束事件、单位以及GF发出前等待是否覆盖仍待核实，不能将本估算说成端到端SLO保证。

### 4.2 估算提案

计算预算 `B = T − W`。用覆盖当前场景且有证据的性能曲线 `f(C)`（非命中Token数C对应的计算及纳入校准范围的固定开销）反求预算内最大可计算长度 `C_max`，进而计算 `r = max(0, 1 − C_max / P90)`。输出参考比例与 P90、T、W、C_max、校准身份、样本数量及条件。r 表示**P90长度请求在该情景下的输入前缀需复用的参考比例**，不是租户整体Token加权命中率门槛，也不是保证。

校准可以从相同部署下已测数据形成离散单调包络或固定chunk时间模型；曲线、拟合及插值规则在提供真实性能数据后确认。以固定8K为参考时，正的剩余长度至少一块，示意计算为 `ceil(C/8192) × 每块时间`，须覆盖尾块及固定开销；8192是批次共享预算，不保证每请求每轮独占，也不证明全部batch等时。优先采用实测覆盖下的模型，拒绝把外部项目predictor直接当作本部署校准。

### 4.3 边界与可解释性

- T和W均需有限非负、单位明确；T为正。B≤0 时返回“该等待情景下无计算预算”，不能给出有保证的比例；即使B>0，也需校准验证缓存读取、首token及固定开销。
- 无有效请求、P90为0、资产身份不明或无适用校准数据，返回不可估算及原因，不输出0或假精确结果。反求超出校准数据范围时标记超范围，不静默外推；命中比例的可实现性、块对齐、前缀分布不由本公式保证。
- 等待为用户输入或有来源的情景值，不能把等待P90和计算P90相加解释为总体P90。P90输入长度并不必然对应P90 TTFT，命中、等待和长度相关性均影响结果；需用同口径实测数据验证误差，证据不足时仅展示条件及不可估算状态。
- 用户侧不同规格可能分流到不同部署；若模型服务跨规格、性能不可视为一致，必须明确估算使用哪个部署/规格及适用样本，不能混用一条曲线。此项的数据获取和归属待确认。

## 5. 组件、数据和协作

沿用V1 CSV校验、统一编码、分组回放、结果存储与读取；扩展时间解析、显式别名初始化和DeepSeek配置，统计侧补充可用于众数均值的等宽箱计数及总和。独立估算组件消费已完成P90和已核实的性能校准，参数或情景变化只重新计算轻量公式，不重放CSV。新统计结果随运行版本及编码资产、模型设置快照记录；查询接口只读既有成果。共享计量/配置修改由本线负责此设计中相应变更，实施前在共享登记明确具体改动的唯一维护方并与MA线对齐；不复制算法或改变MA语义。

统一内网访问涉及监听和暴露面，前端由独立session承接；本稿不固定新接口名称、schema升级方案或部署操作。现有S0 1.0.0和历史结果保持兼容，若必须变更需另行冻结并沟通。

## 6. 验证与审批重点

开发前需对照实际源码与S0确认可行性；建议覆盖：时间格式/UTC与非法输入；现场三模型别名、冲突和既有配置不覆盖；DeepSeek显式模式优先及新旧配置；原JSON tokenization；访问绑定与容器健康检查；排行边界、并列众数、200K以上、空值、排序分页及质量；TTFT公式、校准缺失/超范围/零预算、单位、不同规格与历史结果兼容。数据和性能只使用授权脱敏或合成材料，避免将现场有效子集视为全量。
