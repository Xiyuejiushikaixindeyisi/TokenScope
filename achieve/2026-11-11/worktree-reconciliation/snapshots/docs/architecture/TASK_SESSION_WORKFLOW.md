# 任务与session协作流程

## 当前三角色流程（2026-11-10）

用户只保留研究与产品设计、镜像打包与审查、V3代码修复与开发三个活跃角色；六条V2开发会话休眠。[实际ID及权责](../../memory/SESSIONS.md)。活跃角色各自在本线记忆确认职责，共享登记由当前整理者汇总，避免并发整篇改写。

1. 研究会话负责现场证据/产品范围/宣传、评审和交接，不修改代码；两项评审修订后的开发条件授权见[评审决定](../tasks/product-v3/V3_REVIEW_DECISION_20261110.md)。Token私有修复留V3.5。
2. 新开发会话按已获准四P0计划统一负责公共层/低命中/必要前端兼容的实施、自测与debug；按批闭环后交出确定候选、变更清单、验证证据及已知限制。旧六线不恢复或双写。
3. **开发完成后，由研究/产品设计会话独立验收**，按下方唯一候选冷启动规则核实真实链路，记录问题交开发会话修复并复验；不以改代码或降低门槛替代验收，不直接沿用开发方通过结论。未完成现场业务底线与本地工程验收分开记录。
4. 研究会话据验收结果整理给“镜像打包与审查”的交接prompt，明确候选身份、范围、证据、风险/待现场项、保留与回退要求。镜像会话只审批和授权打包，不承担编码/debug/开发调度或开发验收执行；打包/现场仍按相应授权。
5. 前序登记通知见[回执](../operations/SESSION_SCOPE_REGISTRATION_20261110.md)。通知授权不自动延伸为唤醒休眠线或其他任务；本次职责登记不提前启动验收服务、测试、打包或部署。

首次恢复读AGENTS→CURRENT→SESSIONS→docs/README→自己的ENTRY。冻结契约、统一编码计量、批准四入口/L4L5、旧成果只读与页面访问不触发分析的规则保持。

旧分线/fork/总负责工作流保存在[整理前快照](../../achieve/2026-11-10/v2-session-dormancy/snapshots/docs/architecture/TASK_SESSION_WORKFLOW.md)，已闭环启动和计划见[V2归档](../../achieve/2026-11-10/v2-session-dormancy/README.md)，不作为新任务指令。以下通用规则在相应阶段继续适用。

## 新版本端到端验收必须从干净环境开始

2026-11-02用户明确要求：每次对新版本开展端到端验收，先停止旧版本服务和进程，从干净环境重新开始。本条覆盖旧实践中保留4191/8016等服务、另起端口并行验收的安排；适用于前端自测、联合验收和审查方独立复审。停止旧服务是验收准备，不等于删除旧交付物或授权重新打包。

1. 盘点Windows/WSL中本项目的前端、后端、worker、预览/重定向服务、父子进程及测试容器。记录PID/命令行/工作目录/端口/Compose项目/版本；不能仅凭历史端口或进程名称猜归属。
2. 核实后停止旧版相关服务/进程/容器，确认进程退出、端口释放、旧地址不再服务；不能只换新端口继续依赖旧进程。无关项目、共享Docker daemon不误停；旧state/输入/日志/包/镜像/原证据保留，不使用全局kill或清理。归属不明先核实。
3. 为新候选创建独立运行目录、空白可写state/cache与全新浏览器context/profile，隔离旧localStorage/IndexedDB/HTTP缓存/Service Worker；不清除个人浏览器数据。固定合成输入并通过真实候选后端形成结果；只有明确的恢复/兼容测试才使用历史state隔离副本，不写原件。
4. 从确定源码/新生成dist启动唯一候选环境，记录前后端版本、源码/HTTP资源SHA、实际service_instance_id、PID/URL/命令/state位置。端口名称、旧package版本和SPA fallback的200都不是身份/健康证明。源码验证不冒称新版镜像验证；Docker构建、发布、交付包仍须满足原授权要求。
5. 冷启动通过后另测同一候选的刷新、断网重连、缓存/固定历史和服务重启；清空缓存不能代替恢复测试。留存清理前后进程/端口与启动证据。结束后停止临时辅助进程，注明唯一保留的候选预览（如有）及停止方式；独立复审方重新停止前序候选并冷启动，不直接复用开发方验收现场。

本条不要求在仅整理文档/prompt时停止正在运行的服务；也不授权覆盖生产数据或改变现场停机范围。新候选修复/验收以当前任务授权启动，不把此规则当自动打包或部署指令。

## 设计、开发与契约

用户最新决定确定范围与授权；当前计划管步骤，测试文档管门槛，固定契约管接口，设计管技术依据，实际源码与证据只证明对应版本。B005.1已批准计划/设计/TESTS及S0保留作为维护依据，不重复申请已完成阶段审批。旧prompt与闭环批次是历史，不自动重新授权实施。

授权内按方案→实现→验证修复→问题/测试/结果→记忆推进，普通缺陷自行修复；重大目标、业务语义、接口、门槛或回退改变才与用户讨论。前端额外未知组件/类等重大变化依已有约定讨论。不能删断言换通过，不能把选择器失效直接称后端失败。

后端发布固定S0，消费者记录实际版本/SHA和接收状态；冻结文件不静默修改。接口变化写差异、兼容/迁移与影响，双方登记新版本。假服务、真实后端、真实浏览器、容器、现场证据分层，不互相替代。前端导出内存与完整性规则仍以批准设计为准，不因整理收紧或放宽。

## 入口、归档与协作

P0：AGENTS→CURRENT→本任务ENTRY；P1：当前设计、直接依赖契约、相关源码/测试；P2：按问题追依据；P3：[achieve](../../achieve/README.md)旧批次/旧prompt/日志。不全量重读项目，也不以默认清单禁止必要调查。

每批方案与结果要包含修改范围、依赖身份、测试、问题、偏差和回退。CURRENT只留路由，SESSIONS只留当前分工，历史过程移achieve；原始证据与冻结manifest不改，docs/archive既有快照原位保留。归档路径映射与导航性改动另存清单，不重算历史报告来冒充重测。

共享工作区修改前核对最新状态，按模块责任保留他人工作。文档交接不等于实时通知；不自动创建/唤醒会话、委派子agent、发跨会话消息或设置自动化。个人Git不用PR，按[Git流程](../operations/GIT_WORKFLOW.md)操作；禁止全局reset清理共享修改。
